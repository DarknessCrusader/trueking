# 클라우드컴퓨팅 제1과제 — skills.inc (Solution Architecture) 개념 이해 가이드

이 과제는 Unicorn Tickets 과제와 같은 "EKS 기반 콘서트 예약 앱" 시나리오지만, KMS 정책 세부 조건과 ECR 태그 정책, EKS 네트워크 구조, Prometheus Alertmanager 등에서 결이 다릅니다. **같은 뼈대, 다른 디테일**이라는 관점으로 보면 빠르게 이해됩니다.

## 전체 아키텍처 한눈에 보기
```
User → CloudFront → WAF 연결
          ├─ 루트 경로 → S3(정적 페이지, static/)
          ├─ /booking → ALB(Internet-facing) → EKS(Book App)
          └─ /v1/book → Lambda Function URL → DynamoDB 조회
                              │
                        DynamoDB (App Pod가 PutItem, Lambda가 조회)
```

---

## 1. Networking — Reference01 서브넷 명명 규칙 읽는 법

- `wsc2026-skills-hub-sub-{a,b}` (Public), `wsc2026-skills-app-sub-{a,b}` (Private) — "hub"라는 이름이 붙은 건 Public 서브넷이 IGW로 나가는 관문 역할을 한다는 의미로 이해하면 됩니다. Private 서브넷은 AZ별로 `wsc2026-skills-nat-{a,b}`를 통해 나가므로, 여기서도 지난 과제처럼 **AZ별 NAT 분리**가 기본입니다.

## 2. Application(Book App) — ConfigMap으로 환경변수 분리

- "AWS_REGION, TABLE_NAME을 Dockerfile/Deployment에 직접 적지 말고 ConfigMap으로 관리" — 이건 **12-Factor App**의 "설정은 코드와 분리하여 환경별로 주입한다"는 원칙의 쿠버네티스식 구현입니다. 같은 이미지를 dev/stage/prod에 그대로 재사용할 수 있게 해주는 핵심 이유입니다.
- Deployment의 `envFrom: configMapRef`로 ConfigMap 전체를 환경변수로 주입하는 방식이 일반적입니다.

## 3. Database — 최소 권한을 "테이블 수준"에서

- EKS Pod는 **삽입(PutItem)만**, Lambda는 **조회(Query/GetItem)만** — 같은 테이블이라도 액션 단위로 IAM Policy를 분리해서, "쓰기 전용 클라이언트"와 "읽기 전용 클라이언트"가 서로의 권한을 침범하지 못하게 합니다. 이는 데이터 무결성 관점에서 중요한 설계입니다: 만약 조회용 Lambda가 컴프로마이즈되어도 데이터를 조작할 수는 없습니다.
- GSI를 "booking_id를 이용한 효율적 조회"용으로 만든다는 건, PK가 `client_id`이기 때문에 booking_id로 바로 찾으려면 Scan(비효율)을 해야 하는데 이를 피하기 위해 GSI(PK: booking_id)를 추가로 두는 것 — "메인 테이블 PK와는 다른 조회 축이 필요하면 GSI"라는 원칙이 여기서도 반복됩니다.

## 4. Container Registry — "같은 태그 재업로드 허용, 단 v1 버전은 예외"

- 이 과제는 Unicorn 과제와 정반대 정책입니다: 기본은 **Mutable(태그 재사용 가능)**, 단 `v1.0.0`, `v1.0.1`처럼 버전이 명시된 태그만 **Immutable(불변)**로 만들어야 합니다.
- ECR은 태그 전체에 하나의 Mutability 정책만 걸 수 있는 게 아니라, **Tag Immutability에 예외 패턴을 걸 수 있는 기능(Tag Mutability Exclusion Filters)**을 제공합니다 — 이 과제는 그 기능을 정확히 써야 하는 조건입니다. "버전 태그는 배포 이력 신뢰성을 위해 불변, 나머지(예: dev, test 같은 태그)는 유동적으로 덮어쓰기 허용"하는 실무적으로 흔한 절충안입니다.
- "ECR에는 v1.0.0 이미지를 제외한 이미지가 존재하면 안된다" — 이건 채점 시점의 상태 조건입니다. 개발 중 테스트로 올린 다른 태그의 이미지를 다 지우고 v1.0.0만 남겨야 합니다.

## 5. Container Orchestration — Fully Private + 커스텀 DNS

- **"Fully Private으로 구축"**: Unicorn 과제가 "Control Plane만 비공개"였다면, 이 과제는 **엔드포인트 접근성 자체를 아예 Private로만** 구성하라는 조건입니다 — 클러스터 API든 워크로드든 전부 외부에서 직접 닿을 방법이 없어야 합니다.
- **`*.cluster.local` → `*.wsc2026.skills.local`로 도메인 변경**: 쿠버네티스 내부 서비스 디스커버리(CoreDNS)가 쓰는 기본 도메인을 커스터마이징하는 요구입니다. CoreDNS ConfigMap의 `kubernetes` 플러그인 설정에서 클러스터 도메인을 바꿔야 합니다 — 멀티클러스터 환경에서 도메인 충돌을 피하거나, 조직 표준 네이밍을 적용할 때 실무에서 종종 쓰이는 커스터마이징입니다.
- IAM Role for EKS/NodeGroup을 Administrator 대신 최소 권한으로 — "관리형 서비스라도 기본 제공되는 광범위한 정책을 그대로 쓰지 말고, 실제 필요한 액션만 추린 커스텀 정책을 만들라"는 원칙 재확인입니다.

## 6. Deployment — PDB와 Topology Spread의 조합

- "고가용성 확보를 위해 최소 2대의 Pod를 AZ 간 균등 분산" → **Topology Spread Constraints** (또는 Pod Anti-Affinity)로 구현합니다.
- "노드 드레인/클러스터 업그레이드 시에도 최소 1대 Pod 가용" → **PodDisruptionBudget(PDB)**의 존재 이유입니다. PDB가 없으면 노드 업그레이드 중 모든 Pod가 동시에 내려갈 수 있는데, `minAvailable: 1`(또는 `maxUnavailable` 조정)로 이를 막습니다.
- "동일 가용 영역 내 Pod로 우선 라우팅" → **Service Internal Traffic Policy: Local** 또는 **Topology Aware Routing/Hints**를 가리킵니다. 같은 AZ 안에서 우선 트래픽을 처리하면 Cross-AZ 데이터 전송 비용(그리고 약간의 지연시간)을 절감할 수 있습니다 — 이건 AWS Well-Architected의 "비용 최적화" pillar가 네트워크 트래픽 레벨까지 내려온 구체적 사례입니다.

## 7. S3 Bucket — 버킷 이름에 임의 문자열이 들어가는 이유

- `wsc2026-static-<임의의 영문 4자리>-<비번호>-bucket` — S3 버킷 이름은 전역적으로 유일해야 하므로, 단순히 비번호만 붙이면 다른 대회장/과거 흔적과 충돌할 가능성이 있어 임의 문자열을 추가로 요구하는 것으로 이해하면 됩니다.
- SSE-KMS + **버킷 키(Bucket Key) 활성화**: 버킷 키는 KMS 호출 횟수를 줄여 **비용을 절감**하는 기능입니다(객체마다 KMS API를 매번 호출하는 대신, 버킷 레벨에서 캐싱된 데이터 키를 재사용) — "암호화는 하되 비용도 고려하라"는 Well-Architected 원칙이 반영된 디테일입니다.

## 8. Lambda(GET 조회) — 응답 필드 순서와 시간 포맷까지 맞추기

- "반환되는 컬럼들의 순서가 Response와 정확히 일치해야" — 이건 Python에서 일반 `dict`를 JSON으로 바로 직렬화하면 안 되고, **OrderedDict** 또는 `json.dumps`에 키 순서를 명시적으로 보장하는 방식(Python 3.7+는 사실 dict 자체가 삽입 순서를 유지하므로, 딕셔너리를 구성하는 순서 자체를 Response 스펙과 동일하게 맞추면 됩니다)으로 구현해야 한다는 �스입니다. 채점 스크립트가 JSON 필드 순서까지 비교할 가능성이 있다는 뜻이므로 놓치기 쉬운 디테일입니다.
- `created_at`을 "정해진 포맷으로 변환" — DynamoDB에 저장된 원본 타임스탬프를 Lambda가 응답 시 포맷팅(예: `2026-04-22 14:33:38 KST`)해야 한다는 의미로, 저장 포맷과 표시 포맷을 분리하는 설계입니다.

## 9. Observability — Alertmanager까지 포함된 버전

- Unicorn 과제는 Grafana 대시보드만 요구했다면, 이 과제는 **Prometheus Alertmanager**를 통한 능동적 알림 체계까지 요구합니다 — "메트릭을 보는 것(관측)"과 "임계치를 넘으면 알림을 보내는 것(대응)"은 별개의 컴포넌트가 담당한다는 점을 이해해야 합니다: Prometheus가 룰 평가 후 Alertmanager로 알림을 넘기고, Alertmanager가 실제 라우팅/그룹핑/알림채널 발송을 담당합니다.
- CPU/메모리 임계치 기반 색상 변환(80%↑ 빨강, 60~80% 노랑, 60%↓ 초록) — Grafana 패널의 **Threshold** 설정 기능을 정확히 지정된 값대로 구성해야 하는 디테일입니다.
- 로그 형식이 `{"level":"INFO",...}`처럼 구조화된 JSON — Fluent Bit이 이 로그를 파싱해서 Grafana의 CloudWatch Logs Insights 데이터소스로 쿼리 가능하게 만들어야, 대시보드에서 "레벨별 로그 필터링" 같은 게 가능해집니다.

## 10. Load Balancer / CDN — "잘못된 경로는 403"과 다중 Origin

- ALB Listener Rule에서 알려진 경로(/book, /health 등) 외의 요청엔 명시적으로 403을 반환하는 **Default Action(고정 응답)**을 걸어야 합니다 — 이건 "정의되지 않은 경로는 그냥 지나가게 두지 않고 명시적으로 거부한다"는 화이트리스트 방식의 보안 원칙입니다.
- CloudFront가 3개의 Origin(S3 정적, ALB `/booking`, Lambda `/v1/book`)을 **Path Pattern Behavior**로 라우팅합니다 — 하나의 도메인 뒤에 여러 백엔드를 경로 기반으로 붙이는 API Gateway 없는 "경량 BFF(Backend for Frontend)" 구조라고 볼 수 있습니다.
- 캐싱은 S3만 켜고 ALB/Lambda는 끄는 이유: 정적 콘텐츠는 자주 안 바뀌니 캐싱이 이득이지만, 예약 생성/조회 같은 동적 API 응답을 캐싱하면 사용자마다 다른 결과가 섞여버리는 심각한 버그가 생기기 때문입니다.

**한 줄 요약**: Unicorn 과제와 뼈대는 같지만, 이 과제는 **ECR 태그 정책의 예외 처리, EKS DNS 커스터마이징, PDB/Topology 기반 고가용성, Alertmanager 알림 체계, JSON 필드 순서 같은 "정교함"을 요구하는 디테일 심화 버전**이라고 이해하면 됩니다.
