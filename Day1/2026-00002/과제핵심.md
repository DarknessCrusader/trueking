## λ 모듈 5. Lambda

### "하드코딩 금지" 조건
> **핵심**: DB 연결 정보는 **환경변수**로 관리 (지금까지 반복된 원칙의 직접적 표현)

### ALB 포맷 준수 ⭐ 이 과제만의 함정
> **핵심**: API Gateway 뒤 Lambda와 ALB 뒤 Lambda는 응답 스키마가 다름

- ALB Target Lambda는 `statusCode`, `statusDescription`, `isBase64Encoded`, `headers`, `body` 형식을 정확히 지켜야 함
- 안 지키면 ALB가 응답 해석 못 해 502/500 에러

### 정렬된 GSI 조회
> **핵심**: 애플리케이션 정렬이 아니라 **쿼리 자체에서 정렬**

- `ScanIndexForward: false` 옵션 → GSI Sort Key(`created_at`) 기준 내림차순 반환
- 이게 GSI Sort Key를 `created_at`으로 설계한 이유이기도 함

## 🌍 모듈 6. Load Balancing / CloudFront ⭐ 이 과제의 핵심 차별점

### 커스텀 헤더 검증 vs VPC Origin

| 구분 | Unicorn 과제 | **이 과제** |
|---|---|---|
| ALB 구성 | Internal (인터넷 노출 없음) | **Internet-facing** (열려있음) |
| 우회 차단 방식 | VPC Origin (네트워크 경로 자체 차단) | **CloudFront Custom Header + ALB Listener 조건 검증** |
| 근본 안전성 | 원천 차단 | 헤더값만 알면 이론상 직접 호출 가능 (한계 있음) |
| 시대 | 최신 방식 | 예전부터 널리 쓰인, 여전히 유효한 방식 |

**실제 헤더 흐름**
```
CloudFront → ALB : X-Origin-Verify: wskorea26-cf
CloudFront → S3  : wskorea26-s3-access: true
```
- CloudFront Origin Custom Header 설정으로 비밀 헤더 주입
- ALB Listener Rule의 `http-header` 조건으로 그 값 검증 → 없으면 403
- S3 쪽 헤더는 OAC(SigV4)가 표준 검증 방식이라, 이 헤더는 로깅/디버깅용이거나 채점 스크립트 직접 확인용일 가능성

> **두 과제를 비교하면**: 같은 목적("CloudFront 우회 접근 차단")을 시대가 다른 두 기술로 어떻게 푸는지 보여주는 가장 좋은 대조 사례

### 나머지 CloudFront 요구사항
- HTTP → HTTPS 리다이렉트
- 루트 경로 → S3 웹페이지, 캐싱 활성화
- `/book` 경로 → ALB로 전달

## 📊 모듈 7. Monitoring — 가장 단순화된 버전

> **핵심**: Alertmanager나 로그 구조화 요구 없이 "메트릭+로그 수집→Grafana 시각화" 기본형만

| 요구 메트릭 | 소스 |
|---|---|
| 컨테이너 CPU 사용량 | cAdvisor (kubelet 내장) |
| 컨테이너 메모리 사용량 | cAdvisor |
| 실행중 Pod 개수 | kube-state-metrics |
| 컨테이너 재시작 횟수 | kube-state-metrics |
| 네트워크 트래픽 수신량 | cAdvisor |

- 위 5개는 K8s에서 가장 기본적으로 노출되는 메트릭 → Container Insights나 Prometheus로 바로 스크랩 가능
