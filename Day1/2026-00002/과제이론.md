# 클라우드컴퓨팅 제1과제 — Web Service Provisioning (Korea Skills Concert) 개념 이해 가이드

세 번째 버전입니다. 앞의 두 과제(Unicorn, skills.inc)와 뼈대는 같은 "EKS+CloudFront+Lambda+DynamoDB 콘서트 예약 서비스"지만, **CloudFront-ALB 간 신뢰 검증 방식**과 **네트워크가 4개 서브넷으로 더 단순화**된 점이 특징입니다. 난이도는 상대적으로 낮은 편이라 기본기를 다지기 좋은 버전입니다.

## 전체 아키텍처 한눈에 보기
```
User → CloudFront (HTTPS 강제)
          ├─ 루트 경로 → S3 (정적 웹, /web/main/)
          └─ /book → ALB(Internet-facing, but CloudFront 통해서만 유효) → EKS(Book App)
                                                                              │
                                                                        DynamoDB
                                                                              ▲
                                                                    Lambda (/reserv-query, GET)
```

---

## 1. Networking — 4개 서브넷으로 단순화된 이유

- Public 2개(`pub-subnet-{c,d}`) + Private 2개(`priv-subnet-{c,d}`), AZ는 c/d 두 곳만 사용 — 앞의 두 과제(3 AZ)보다 AZ 수가 적습니다. "다이어그램은 추상화된 것이며 서브넷 개수는 요구사항에 따라 다를 수 있다"는 유의사항이 이런 차이를 미리 안내하고 있습니다. **핵심은 AZ 개수 자체가 아니라 "고가용성을 위해 최소 2개 이상의 AZ에 걸쳐 구성"이라는 원칙**입니다.
- Private 서브넷도 AZ별 NAT(`book-ngw-{c,d}`)로 분리 — 지금까지 계속 반복된 "AZ 장애 격리" 원칙 그대로입니다.

## 2. S3 — Object Path 지정의 의미

- `/web/main/` 경로에 index.html, main.jpeg를 업로드 — 버킷 루트가 아니라 특정 프리픽스 아래 정적 파일을 두는 건, 나중에 같은 버킷에 다른 용도의 객체(로그, 다른 앱 자산 등)를 함께 둘 수 있도록 네임스페이스를 분리해두는 관행입니다.
- CloudFront가 루트 경로(`/`) 요청을 이 프리픽스(`/web/main/index.html`)로 매핑해야 하므로, **Origin Path** 설정(CloudFront Origin 레벨에서 요청 경로 앞에 프리픽스를 자동으로 붙여주는 기능)을 써야 합니다.

## 3. NoSQL Database — GSI를 "콘서트별 조회"에 최적화

- PK: `client_id`, GSI: `concert_name`(PK) + `created_at`(SK) — 메인 테이블은 "고객 기준" 조회, GSI는 "콘서트 기준으로 예약을 최신순 조회"하는 축입니다. 이 패턴은 이미 여러 번 보셨을 텐데, **"메인 키로 커버 안 되는 조회 패턴은 무조건 GSI"**라는 원칙이 매 과제마다 이름만 바뀌어 반복되는 걸 다시 확인할 수 있습니다.
- Reference03에서 "GET /reserv-query가 concert_name으로 조회"하는데, 바로 이 GSI를 Lambda가 Query하게 되는 겁니다 — DB 설계와 API 설계가 어떻게 맞물리는지 보여주는 좋은 예시입니다.

## 4. EKS — 특정 서브넷 고정 지정과 노드그룹 분리

- `Subnet: wskorea26-priv-subnet-c, wskorea26-priv-subnet-d`처럼 **EKS 클러스터가 사용할 서브넷을 명시적으로 지정**합니다 — Private 서브넷에만 노드가 뜨도록 하기 위한 조건이며, 이후 나올 "addon/app 노드그룹 분리(taint)" 패턴을 다시 활용합니다.
- Addon/App NodeGroup 분리는 이제 익숙하실 패턴({node-type: addon}, {node-type: app} 라벨) — 매 과제마다 라벨 키/값만 바뀌고 구조는 동일합니다.

## 5. Lambda — "하드코딩 금지" 조건이 가리키는 것

- "Lambda가 DynamoDB에 연결하기 위해 필요한 값은 함수에 하드코딩되면 안된다" — 테이블 이름 같은 값을 **환경변수(Environment Variable)**로 관리하라는 뜻입니다. 앞선 과제들의 "TABLE_NAME 환경변수" 요구사항과 같은 원칙이지만, 여기선 "하드코딩 금지"라는 표현으로 더 직접적으로 명시되어 있습니다.
- ALB 포맷을 따르는 Lambda 응답 — ALB가 Lambda를 Target으로 쓸 때는 API Gateway와 다른 응답 스키마(`statusCode`, `statusDescription`, `isBase64Encoded`, `headers`, `body` 등)를 요구합니다. 이 포맷을 안 지키면 ALB가 Lambda 응답을 제대로 해석하지 못해 502/500 에러가 납니다 — Lambda를 API Gateway 뒤에 두는 것과 ALB 뒤에 두는 것의 구현 차이를 정확히 알아야 하는 포인트입니다.
- 조회 결과가 "데이터베이스 레벨에서 최신순 정렬" — DynamoDB Query 시 `ScanIndexForward: false` 옵션을 쓰면 Sort Key(`created_at`) 기준 내림차순으로 결과가 반환됩니다. 애플리케이션에서 별도로 정렬하지 말고 **쿼리 자체에서 정렬된 결과를 받으라**는 의미로, 이게 GSI의 Sort Key를 `created_at`으로 설계한 이유이기도 합니다.

## 6. Load Balancing / CloudFront — 커스텀 헤더 검증 방식 (VPC Origin과의 차이 이해하기)

이 과제가 앞의 두 과제와 가장 다른 지점입니다.

- Unicorn 과제는 **VPC Origin**으로 ALB를 아예 인터넷에 노출하지 않는 방식을 썼지만, 이 과제는 **ALB를 Internet-facing으로 열어두되, CloudFront가 보내는 요청에만 커스텀 헤더(`X-Origin-Verify: wskorea26-cf`)를 붙이고, ALB 리스너 규칙에서 그 헤더가 없으면 403을 반환**하는 방식입니다.
- 이건 VPC Origin 기능이 생기기 전부터 널리 쓰이던 **"우회 접근 방지" 구식이지만 여전히 유효한 패턴**입니다: CloudFront Origin Custom Header 설정으로 비밀 헤더를 주입하고, ALB Listener Rule의 조건(`http-header`)으로 그 값을 검증합니다.
- 이 방식의 한계(그래서 최근엔 VPC Origin을 더 권장하는 이유)는, 헤더 값 자체는 "비밀"이지만 ALB가 여전히 퍼블릭 IP를 가지고 있어 **이론적으로는 그 헤더 값만 알면 누구나 직접 호출할 수 있다**는 점입니다. 반면 VPC Origin은 애초에 네트워크 경로 자체가 막혀있어 더 근본적인 차단입니다. 두 과제를 비교해보면 "같은 목적(우회 접근 차단)을 달성하는 두 가지 다른 시대/방식의 기술"을 배울 수 있습니다.
- S3로 전달하는 요청에 `wskorea26-s3-access: true` 헤더를 포함해야 한다는 조건도 있는데, S3는 원래 Origin Custom Header 자체를 그대로 활용하기보다 **OAC(SigV4 서명)**로 검증하는 게 표준이라, 이 헤더는 아마 로깅/디버깅용이거나 채점 스크립트가 직접 확인하는 항목일 가능성이 높습니다 — 문제에 명시된 그대로 정확히 설정하는 게 중요합니다.

## 7. Monitoring — 가장 단순화된 관측 구성

- 이 과제는 Alertmanager나 세밀한 로그 구조화 요구 없이, **"클러스터 메트릭 + Pod 로그를 CloudWatch로 보내고 Grafana로 시각화"**라는 기본형만 요구합니다 — Unicorn/skills.inc 과제보다 요구 난이도가 낮은 버전이라고 볼 수 있습니다.
- 요구된 5개 메트릭(CPU, 메모리, 실행 Pod 수, 재시작 횟수, 네트워크 수신량)은 Kubernetes에서 가장 기본적으로 노출되는 컨테이너 메트릭들로, `kube-state-metrics` + `cAdvisor`(kubelet에 내장)를 CloudWatch Container Insights나 Prometheus로 스크랩하면 바로 얻을 수 있는 값들입니다.

## 8. wskorea26-vpc-environment-sg — 앞 과제의 CloudShell VPC Environment와 같은 목적

- Unicorn 과제의 `unicorn-mark` CloudShell VPC Environment와 동일한 역할을 하는 보안그룹입니다. "외부에서 접근해 EKS Cluster에 접근할 수 있어야 한다"는 조건은, 채점 위원이 CloudShell 등에서 `kubectl`로 클러스터를 검증할 수 있는 경로를 확보하기 위한 것 — **채점 편의를 위한 예외 접근 경로**라는 점에서 앞의 다른 과제 유의사항들과 같은 목적입니다.

**한 줄 요약**: 이 과제는 세 버전 중 가장 "표준적이고 단순화된" 버전으로, VPC Origin 대신 **커스텀 헤더 검증 방식**을 쓴다는 점이 가장 큰 차별점입니다. 나머지(GSI 설계, taint 기반 노드그룹 분리, Lambda 환경변수, 정렬된 GSI 조회)는 앞의 두 과제와 원리가 완전히 동일하니, 세 과제를 함께 비교하며 공부하면 "같은 요구사항이 표현만 바뀌어 반복된다"는 걸 확실히 체득할 수 있습니다.
