# 클라우드컴퓨팅 제1과제 — Unicorn Tickets (콘서트 예약 플랫폼) 개념 이해 가이드

이 과제는 지금까지 본 제2과제(4개 독립 모듈)와 달리, **하나의 완결된 아키텍처를 처음부터 끝까지 구축**하는 유형입니다. Diagram 순서를 따라가면서 "왜 이 구성요소가 이 자리에 있는가"를 이해하는 게 핵심입니다.

## 전체 아키텍처 한눈에 보기
```
User → WAF(us-east-1) → CloudFront → [정적페이지: S3(OAC)]
                              │
                              └→ [/v1/book GET → Lambda Origin]
                              └→ [POST, /health → VPC Origin → Internal ALB]
                                                                    │
                                                       [EKS Private Subnet]
                                                       ├─ App NodeGroup (Book App Pod)
                                                       │    └─ Fluent Bit → CloudWatch
                                                       └─ Addon NodeGroup (Prometheus, Grafana)
                                                                    │
                                                              DynamoDB (GSI로 Lambda가 조회)
```

---

## 1. Networking — 왜 6개 서브넷이고, App은 왜 인터넷을 안 거치나

- **3 AZ × 2계층(Public/Private) = 6개 서브넷**: 앞선 과제들과 같은 고가용성 원칙이지만, 여기선 **Private 서브넷마다 개별 NAT(unicorn-nat-{a,b,c})와 개별 라우팅 테이블**을 요구한다는 게 다릅니다. 하나의 공용 NAT를 쓰면 그 AZ가 죽었을 때 다른 AZ의 Private 서브넷까지 인터넷이 끊기므로, **AZ 장애 격리(Blast Radius 최소화)**를 위해 NAT도 AZ별로 분리합니다.
- **"컨테이너 이미지 다운로드 및 로그/메트릭 export 시 외부 인터넷을 경유하지 않아야 한다"** — 이건 NAT를 안 쓰라는 뜻이 아니라, **VPC Endpoint(ECR, S3, CloudWatch Logs 등에 대한 PrivateLink)**를 구성해서 AWS 내부망으로만 트래픽이 흐르게 하라는 요구입니다. NAT를 거치면 결국 "인터넷 경유"로 간주되기 때문에, 이 조건을 만족하려면 각 서비스별 VPC Endpoint(Interface/Gateway)가 필요합니다.
- **Zero Subnet 허용**: `/24`인데 AZ가 3개, 계층이 2개면 총 6개 서브넷이 필요합니다. `10.97.0.0/24`, `.1.0/24`, `.2.0/24`(Public), `.10.0/24`, `.11.0/24`, `.12.0/24`(Private)처럼 CIDR을 순서대로 배정하되, 0번째 서브넷(Zero Subnet, 예전엔 예약되어 쓰지 못했던)도 이제 정상 사용 가능하다는 걸 알려주는 것입니다.

## 2. KMS — 왜 키를 3개로 쪼개는가

- `unicorn-kms-app`, `unicorn-kms-data`, `unicorn-kms-platform` — 이렇게 **용도별로 키를 분리**하는 이유는, 키 하나가 노출/로테이션 문제가 생겨도 영향 범위를 해당 도메인으로 한정하기 위해서입니다(Blast Radius 원칙이 KMS에도 적용). 또한 각 팀/서비스가 자신의 키만 접근하도록 Key Policy를 세분화할 수 있습니다.
- **90일 자동 키 교체(Automatic Key Rotation)**: 키를 물리적으로 바꿔도 기존 데이터는 이전 키 버전으로 계속 복호화 가능합니다(KMS가 내부적으로 버전을 관리) — "키를 주기적으로 갱신하되 기존 암호화 데이터의 접근성은 깨지지 않는" AWS KMS의 특징을 이해하고 있어야 합니다.
- **Platform Key만 us-east-1 다중 리전 키인 이유**: WAF는 반드시 us-east-1(CloudFront 연결용 WAF의 특성)에서 생성되고, 그 로그를 암호화해야 하므로, 서울 리전 키로는 us-east-1 리소스를 암호화할 수 없습니다. **Multi-Region Key**는 여러 리전에서 동일한 키 자료를 공유하는 KMS 키로, 리전 경계를 넘는 암호화 요구를 해결하는 방법입니다.

## 3. S3 — 정적 프론트엔드

- Private + 버전 관리 + Data CMK 암호화 — 이 조합은 "누가 실수로 파일을 지워도 이전 버전으로 복구 가능"하게 하면서, 동시에 저장 데이터를 암호화하는 표준 조합입니다. CloudFront OAC(뒤에서 다룸)와 짝을 이뤄야 완성됩니다.

## 4. DynamoDB — GSI 설계 다시 보기

- PK: `booking_id` (개별 예약 단위 조회), GSI: PK `client_id` + SK `created_at` — 이건 지난 과제들에서 여러 번 봤던 패턴입니다: **원본 테이블은 "예약 자체"를 조회하는 축, GSI는 "고객별 예약 이력을 최신순으로" 조회하는 축**으로 나뉩니다.
- App CMK로 암호화 + PITR + 삭제 방지(Deletion Protection) — 결제/예약 데이터처럼 "복구 불가능하면 치명적인" 데이터에 흔히 적용하는 3종 보호 세트입니다.

## 5. ECR — 취약점 스캔과 태그 불변성

- **"공개된 취약점이 존재해서는 안된다"**: ECR의 이미지 스캔(Scan on Push) 기능을 활성화해서, CVE가 발견된 이미지는 배포하지 말아야 한다는 뜻 — 실무에서 "빌드 파이프라인에 보안 게이트를 넣는다"는 개념의 축소판입니다.
- **"latest를 제외한 태그의 중복 불허"**: ECR의 **Tag Immutability**(태그 불변성) 설정을 태그 단위로 다르게 적용해야 한다는 뜻입니다 — `v1.0.0` 같은 버전 태그는 한 번 push되면 다시 덮어쓸 수 없어야 하고(불변, 배포 이력의 신뢰성 보장), `latest`만 예외적으로 계속 갱신 가능해야 합니다.

## 6. EKS — 이 과제의 핵심 심화 포인트

### Control Plane 비공개 + 모든 로그 수집
- "외부에서 접근 불가"는 EKS Cluster Endpoint Access를 **Private로 설정**하라는 뜻입니다. Public 접근을 끄면, 클러스터 API를 조작하려면 VPC 내부(또는 VPN/Direct Connect)에서만 가능합니다 — 그래서 유의사항 14번의 **unicorn-mark CloudShell VPC Environment**가 필요한 겁니다(외부에서 클러스터를 다루는 유일한 창구를 VPC 내부의 CloudShell로 만든 것).
- Etcd Secrets, EBS, 로그를 전부 Platform CMK로 암호화 — EKS의 **Envelope Encryption**(Secrets를 KMS로 한 번 더 감싸서 암호화)이라는 특정 기능을 가리킵니다. etcd 자체가 탈취돼도 Secret 값이 그대로 노출되지 않도록 하는 심층 방어입니다.

### App/Addon NodeGroup 분리 — taint의 재확인
- 지난 과제들에서 봤던 것과 동일한 원리(taint로 App/Addon 물리 분리)입니다. 여기선 App NodeGroup을 "AZ별로 균등하게 총 2대 이상"으로 명시 — Pod가 아니라 **Node 자체의 AZ 분산**을 요구한다는 점에 유의하세요. Node가 한 AZ에 몰리면 그 AZ 장애 시 App 전체가 죽습니다.

### EKS Access Entry — 왜 aws-auth ConfigMap을 쓰지 말라고 하나
- 예전 EKS는 클러스터 인증을 `aws-auth`라는 ConfigMap을 수동으로 편집해서 관리했습니다. 이 방식은 **누가 무슨 권한을 갖는지 Kubernetes 오브젝트 안에 숨어있어 추적/감사가 어렵고, 실수로 잘못 편집하면 클러스터 접근이 통째로 막히는 리스크**가 있었습니다.
- **EKS Access Entry**는 이 인증 매핑을 AWS API/IAM 레벨에서 관리하는 최신 방식으로, IAM Policy처럼 버전 관리·감사·최소 권한 부여가 쉬워집니다. "관리 방식을 AWS 네이티브로 통합한다"는 최근 EKS 트렌드를 보여주는 요구사항입니다.

### Pod Identity — IRSA의 다음 세대
- 이전 과제들에서 IRSA(ServiceAccount에 role-arn annotation)를 봤는데, 여기서는 **Pod Identity**를 씁니다. 개념은 동일(Pod에 세밀한 IAM Role을 부여)하지만, Pod Identity는 OIDC Provider 설정 없이 **EKS Pod Identity Agent**라는 애드온이 자동으로 자격증명을 주입해주는 더 단순화된 최신 방식입니다.
- "Trust Policy가 본 클러스터에서만 사용 가능하도록 명시" — Role을 Assume할 수 있는 조건을 이 EKS 클러스터로 한정한다는 뜻으로, 다른 클러스터나 계정에서 이 Role을 도용하지 못하게 막는 조건입니다.

### Graceful Shutdown — 왜 preStop + terminationGracePeriodSeconds인가
- Pod가 종료 신호(SIGTERM)를 받으면 즉시 죽는 게 아니라, **preStop hook**으로 "잠시 대기하며 로드밸런서가 이 Pod를 트래픽 대상에서 빼도록 시간을 벌고", 그 사이 진행 중이던 요청은 마무리할 시간을 `terminationGracePeriodSeconds`로 확보합니다. 배포/노드교체 중 사용자 요청이 끊기는 걸 막는 표준 패턴입니다.

## 7. Lambda — 예약 조회

- ALB에서 Lambda를 직접 호출하는 구조(Lambda Target Group)입니다. Optional Query String 조건(email, concert_name)을 모두 만족하는 AND 조건 검색을 구현해야 하는데, DynamoDB GSI(client_id/created_at) 하나로는 이 모든 조합을 커버 못 하므로 **Query 후 애플리케이션 레벨 필터링**이 필요할 수 있습니다.

## 8. Service Endpoint — Internal ALB + VPC Origin의 조합이 핵심

- **왜 Internal ALB인가**: "CloudFront를 거치지 않는 요청을 전부 거절"하려는 게 목적인데, 예전엔 이걸 위해 ALB를 Public으로 열고 커스텀 헤더 검증을 하는 방식(뒤에 나오는 skills.inc 과제가 이 방식)을 많이 썼습니다. 이 과제는 아예 **Internal ALB**(퍼블릭 IP가 없어 인터넷에서 원천적으로 도달 불가)로 만들고, CloudFront의 **VPC Origin**이라는 최신 기능으로 연결합니다.
- **VPC Origin**: CloudFront가 VPC 내부의 리소스(Internal ALB 등)에 인터넷을 거치지 않고 직접 도달할 수 있게 해주는 기능입니다. 예전엔 이런 구조를 만들려면 Public ALB + SG로 CloudFront IP만 허용 + 커스텀 헤더 검증을 조합해야 했는데, VPC Origin은 이 문제를 근본적으로 해결(애초에 인터넷 노출 자체가 없음)합니다 — VPC Lattice의 Managed Prefix List와 비슷한 "우회 접근 원천 차단" 철학입니다.
- **GET → Lambda, POST/health → Book App**: CloudFront가 아니라 **ALB의 Listener Rule(경로/메서드 기반 라우팅)**에서 이 분기를 처리합니다.

## 9. WAF — 반드시 us-east-1인 이유

- CloudFront에 연결하는 WAF WebACL은 **항상 us-east-1(글로벌 서비스인 CloudFront의 특성)**에 만들어야 합니다 — AWS의 고정 제약사항입니다.
- Rate-Based Statement(60초 50건)는 "짧은 시간에 비정상적으로 많은 요청을 보내는 클라이언트"를 IP 단위로 자동 차단하는 기능 — DDoS/크롤링/부하테스트성 공격에 대한 1차 방어선입니다.
- Managed Rule Groups(Common, KnownBadInputs)는 AWS가 관리하는 "이미 알려진 공격 패턴 시그니처 모음"을 그대로 적용하는 것 — SQLi, XSS 같은 공격을 직접 룰을 짜지 않고도 방어할 수 있게 해줍니다.

## 10. Security(Audit Role) — Assume Role의 이중 잠금

- "동일 계정의 IAM Principal이 External ID와 함께 Assume" — 이건 **Confused Deputy 공격 방지**를 위한 표준 패턴입니다. Trust Policy에 특정 Principal을 허용하는 것만으로는, 그 Principal을 통해 제3자가 실수로/악의로 Role을 Assume하게 만들 수 있는 여지가 있는데, **External ID라는 추가 비밀값**을 조건으로 걸면 그 값을 아는 사람만 실제로 Assume이 성공합니다.
- 세션 1시간 제한 + Inline Policy + 와일드카드 금지 — "감사용 계정이 탈취되더라도 오래/넓게 사용되지 못하게" 시간과 권한 범위를 동시에 좁히는 설계입니다.

## 11. Observability — Fluent Bit + Prometheus/Grafana 조합

- Fluent Bit DaemonSet → CloudWatch Logs (10초 이내, /health 로그 제외) — "헬스체크 로그"는 초당 여러 번 발생해 노이즈만 키우므로 필터링해서 제외하는 게 실무에서도 흔한 관행입니다. Fluent Bit의 필터 플러그인으로 특정 경로의 로그를 걸러낼 수 있습니다.
- Prometheus/Grafana를 EKS 위에 설치형으로 구성 — CloudWatch만으로는 세밀한 Pod/컨테이너 메트릭(요청 지연시간 분포 등)을 다루기 번거롭기 때문에, 쿠버네티스 네이티브 모니터링 스택을 추가로 둡니다. "관리형 Control Plane 컴포넌트는 메트릭 수집 대상에서 제외"라는 조건은, EKS가 완전관리형이라 애초에 사용자가 접근할 수 없는 Control Plane 내부(etcd 등)는 스크랩 대상이 될 수 없다는 걸 명시한 것입니다.

**한 줄 요약**: 이 과제는 "Private-first EKS(Access Entry, Pod Identity, Envelope Encryption) + VPC Origin으로 완전히 인터넷 우회 없는 CDN 연결 + 용도별 KMS 분리 + Assume Role 이중 잠금"까지, 지금까지 본 패턴들의 최신/심화 버전을 모아놓은 종합 문제라고 볼 수 있습니다.
