## 🌐 모듈 1. Networking

### `unicorn-vpc` (10.97.0.0/16)
> **핵심**: 3AZ × 2계층 = 6서브넷, AZ별 NAT 완전 분리로 장애 격리

| 계층 | 서브넷명 | 개수 |
|---|---|---|
| Public | `unicorn-subnet-pub-{a,b,c}` | 3 |
| Private | `unicorn-subnet-priv-{a,b,c}` | 3 |

- **AZ별 개별 NAT(`unicorn-nat-{a,b,c}`) + 개별 라우팅 테이블(`unicorn-rt-priv-{a,b,c}`)**
  - 공용 NAT 하나만 쓰면 그 AZ 장애 시 다른 AZ Private까지 인터넷 끊김 → AZ별 분리로 Blast Radius 최소화
- **Public은 `unicorn-rt-pub` 공용** — Public은 상태 없는 경로라 공유해도 장애 전파 리스크 낮음
- **"인터넷 경유 없이 이미지 다운로드/로그 export"** → NAT가 아니라 **VPC Endpoint(ECR, S3, CloudWatch Logs 등 PrivateLink)** 구성 필요
- **VPC Flow Log 활성화** → 네트워크 트래픽 감사/트러블슈팅 근거 데이터

## 🔐 모듈 2. KMS

### 3개 CMK — 용도별 분리
> **핵심**: 키 하나가 노출돼도 영향 범위를 그 도메인으로 한정 (Blast Radius 원칙)

| Alias | 암호화 대상 |
|---|---|
| `unicorn-kms-app` | Secrets Manager, DynamoDB |
| `unicorn-kms-data` | S3, ECR |
| `unicorn-kms-platform` | EKS Envelope Encryption, EBS, Log |

- **90일 자동 키 교체**: 키를 갱신해도 기존 데이터는 이전 버전으로 계속 복호화 가능 (KMS 내부 버전 관리)
- **Platform Key만 us-east-1 다중 리전 키**: WAF는 항상 us-east-1(CloudFront 특성) → 서울 리전 키로는 그 리소스를 암호화할 수 없음 → Multi-Region Key로 리전 경계 해결

## ☸️ 모듈 6. EKS ⭐ 이 과제의 핵심 심화 모듈

### `unicorn-eks-cluster` (v1.35)
> **핵심**: Control Plane 완전 비공개 + 모든 로그 수집 + 최신 인증 방식

- **Control Plane Endpoint: Private만** → 외부에서 API 조작 불가 → 그래서 `unicorn-mark` CloudShell VPC Environment(Private Subnet 내부)가 유일한 조작 창구
- **Etcd Secrets + 모든 EBS + 모든 로그 → Platform CMK 암호화**
  - **Envelope Encryption**: etcd가 탈취돼도 Secret 값이 그대로 노출되지 않는 심층 방어

### Addon NodeGroup
> **핵심**: Taint로 App과 물리 분리 (익숙한 패턴)

| 항목 | 값 |
|---|---|
| Label | `{"unicorn": "addon"}` |
| Node Tag | `unicorn-k8snode-addon-node` |
| 최소 대수 | 1대 |

### App NodeGroup
| 항목 | 값 |
|---|---|
| Label | `{"unicorn": "app"}` |
| Node Tag | `unicorn-k8snode-app-node` |
| 최소 대수 | AZ별 균등, 총 2대 이상 |

> **Node 자체의 AZ 분산**이 요구됨 — Pod가 아니라 Node가 한 AZ에 몰리면 그 AZ 장애 시 App 전체 사망

### K8s Configuration — Book App
| 리소스 | 이름 |
|---|---|
| Namespace | `unicorn` |
| Deployment | `unicorn-book-app-deploy` |
| Service | `unicorn-book-app-svc` |
| 컨테이너명 | `book` |

- **Liveness/Readiness Probe** (`/health`): 비정상 Pod 자동 재시작 + 준비 안 된 Pod엔 트래픽 차단
- **Graceful Shutdown (preStop hook + terminationGracePeriodSeconds)**
  - SIGTERM 즉시 죽지 않고, preStop이 "LB에서 빠질 시간"을 벌고 그 사이 진행 중 요청을 마무리
  - 배포/노드교체 중 요청 유실 방지의 표준 패턴

### Security — EKS Access Entry & Pod Identity
> **핵심**: 예전 방식(aws-auth ConfigMap, IRSA)의 최신 대체재

| 구분 | 예전 방식 | 이 과제가 쓰는 방식 | 차이 |
|---|---|---|---|
| 클러스터 인증 | `aws-auth` ConfigMap | **EKS Access Entry** | ConfigMap 수동 편집 리스크 없이 IAM API 레벨로 감사/관리 |
| Pod IAM 권한 | IRSA (OIDC 필요) | **Pod Identity** | OIDC Provider 설정 없이 Pod Identity Agent가 자동 자격증명 주입 |

- **Trust Policy가 "본 클러스터에서만 사용 가능"**: 다른 클러스터/계정에서 이 Role 도용 방지

## 🌍 모듈 8. Service Endpoint

### `unicorn-alb` (Internal ALB) ⭐ 핵심
> **핵심**: 퍼블릭 IP 자체가 없어 인터넷에서 원천적으로 도달 불가

- CloudFront를 거치지 않는 요청(내부망 포함)을 전부 거절하려는 목적
- ALB Listener Rule에서 GET→Lambda, POST/GET `/health`→Book App 경로/메서드 분기

### `unicorn-svc-cf` (CloudFront) — **VPC Origin** ⭐ 이 과제의 최신 기법
> **핵심**: CloudFront가 인터넷을 거치지 않고 VPC 내부 리소스(Internal ALB)에 직접 도달

| 구분 | 예전 방식 | 이 과제가 쓰는 방식 |
|---|---|---|
| ALB 노출 | Public ALB + SG로 CloudFront IP만 허용 + 커스텀 헤더 검증 | **Internal ALB + VPC Origin** |
| 우회 가능성 | 헤더값만 알면 이론상 직접 호출 가능 | 애초에 네트워크 경로 자체가 없어 원천 차단 |

- S3 Origin은 OAC로, ALB Origin은 VPC Origin으로 — 두 origin 모두 "우회 접근 불가"라는 같은 목표를 다른 메커니즘으로 달성

### `unicorn-waf` (us-east-1 필수)
> **핵심**: CloudFront 연결 WAF는 항상 us-east-1 (AWS 고정 제약)

- Managed Rule Groups: `AWSManagedRulesCommonRuleSet`, `AWSManagedRulesKnownBadInputsRuleSet`
- Custom Rule `unicorn-rate-limit`: 60초 내 IP당 50건 초과 시 차단 → DDoS/크롤링 1차 방어선
- 차단 응답: HTTP 403 "Request blocked by Unicorn WAF"
- 로그 → `aws-waf-logs-unicorn` (Platform CMK 암호화)

## 🔑 모듈 9. Security (Audit Role)

### Assume Role의 이중 잠금 ⭐ 핵심 이론
> **핵심**: Confused Deputy 공격 방지 — Principal 허용만으론 부족, External ID로 한 번 더 잠금

- 동일 계정 IAM Principal + **External ID** 함께 Assume해야만 성공
- External ID 없거나 불일치 → Assume 거부
- 세션 1시간 제한 + Inline Policy + 와일드카드 금지 → "탈취돼도 오래/넓게 못 씀"
- 권한 범위: DynamoDB 조회 + VPC/EKS Describe만

- 패널: 노드 CPU/Memory(Time Series), Pod 상태(Stat+graph), Book App Ready Pod 수(Stat), HTTP 응답시간(Time Series)

## 🎯 핵심 이론 요약

| 이론 개념 | 정의 | 적용 사례 |
|---|---|---|
| Blast Radius 최소화 | 장애/유출 영향 범위를 최소 단위로 제한 | AZ별 NAT, 용도별 KMS 키 |
| Envelope Encryption | 데이터를 한 번 더 감싸 암호화하는 심층 방어 | EKS etcd Secrets |
| 최신 인증 체계로의 전환 | 수동 ConfigMap → API 기반 선언적 관리 | EKS Access Entry, Pod Identity |
| 완전한 네트워크 격리 | 애초에 도달 경로 자체를 없앰 | VPC Origin (Internal ALB) |
| Graceful Shutdown | 종료 신호 후 유예 시간 확보로 요청 유실 방지 | preStop + terminationGracePeriodSeconds |
| Confused Deputy 방지 | 추가 비밀값(External ID)으로 Assume 이중 검증 | Audit Role |
