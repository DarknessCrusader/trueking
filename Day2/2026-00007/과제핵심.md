# 클라우드컴퓨팅 제2과제 — 완벽 이해 가이드

이 과제는 4개의 독립된 모듈로 구성되어 있고, 리전도 각각 다릅니다. 각 모듈은 사실 **"실무에서 흔히 쓰는 아키텍처 패턴 하나씩"**을 압축해서 담아놓은 것이기 때문에, 패턴의 목적을 이해하면 문제를 안 외워도 자연스럽게 풀 수 있습니다.

| 모듈 | 리전 | 핵심 주제 |
|---|---|---|
| 1. NoSQL | ap-southeast-1 | DynamoDB 동시성 제어 + Streams 이벤트 처리 |
| 2. CDN Function | us-east-1 | CloudFront 엣지 컴퓨팅 + A/B 테스팅 |
| 3. EKS Scaling | ap-northeast-2 | Queue 기반 Pod/Node 오토스케일링 |
| 4. Container Logging | ap-northeast-1 | 쿠버네티스 로그 파이프라인 (수집→저장→시각화) |

---

## 모듈 1. NoSQL — "좌석 하나를 두 사람이 동시에 예약하면 어떻게 될까?"

### 이 모듈이 테스트하려는 것
기차 좌석 예매처럼 **동시에 여러 사람이 같은 리소스를 놓고 경쟁**하는 상황에서, 데이터 정합성을 어떻게 지키는가입니다. RDB의 트랜잭션/락 없이, DynamoDB만으로 이걸 어떻게 해결하는지가 핵심입니다.

### 1) 테이블 설계가 왜 이렇게 되어있나
- **Reservation Table**: PK = `train_id`, SK = `seat_id` → "이 기차의 이 좌석"이 하나의 아이템(row)이 됩니다. 좌석 단위로 아이템을 쪼갠 이유는, 좌석마다 독립적으로 락(조건부 쓰기)을 걸기 위해서입니다.
- **GSI (gsi-user-reservations)**: PK = `user_id`, SK = `reserved_at` → 기본 테이블은 "기차 기준"으로만 조회가 빠른데, "이 사용자가 예약한 좌석들"을 조회하려면 다른 인덱스가 필요합니다. 이게 GSI의 존재 이유입니다.
  - **핵심 포인트**: "예약 안 된 좌석은 GSI에 없어야 한다" → DynamoDB GSI는 **Sparse Index**입니다. 즉 아이템에 GSI의 PK/SK 속성(`user_id`, `reserved_at`)이 **아예 없으면** 그 아이템은 GSI에 나타나지 않습니다. 그래서 예약 취소 시 `user_id`/`reserved_at` 속성 자체를 `REMOVE`(삭제)해야 GSI에서 자동으로 빠집니다. status만 "cancelled"로 바꾸는 게 아니라는 점이 중요합니다.

### 2) Conditional Write — 동시성 제어의 핵심
- 두 사람이 동시에 같은 좌석을 예약 요청하면, 둘 다 "성공"이 되면 안 됩니다.
- DynamoDB의 `UpdateItem`에 **ConditionExpression**을 걸면: "지금 status가 available일 때만 업데이트를 허용"하도록 만들 수 있습니다.
- 동시에 두 요청이 들어와도 DynamoDB는 내부적으로 요청을 순차 처리하므로, 먼저 도착한 요청만 조건을 만족해 성공하고, 나중 요청은 조건이 깨져서 `ConditionalCheckFailedException`이 발생 → 이걸 잡아서 **409**로 응답해야 합니다.
- `version`을 1씩 증가시키는 건 낙관적 동시성 제어(Optimistic Concurrency Control)의 전형적인 패턴 — 나중에 "이 예약이 몇 번째로 바뀐 상태인지" 추적할 수 있게 해줍니다.

### 3) Streams → Lambda — 이벤트 기반 후처리
- DynamoDB Streams는 테이블에 변경(Insert/Update/Delete)이 생길 때마다 그 변경 내역을 스트림으로 흘려보내는 기능입니다.
- `NEW_AND_OLD_IMAGES`로 설정하면 "변경 전/후 데이터"를 둘 다 Lambda가 받을 수 있습니다 (예: 취소 시 "누가 취소했는지"를 old image에서 알아낼 수 있음).
- Lambda가 이 스트림을 트리거로 받아 Audit 테이블에 기록 → **감사 로그(누가, 언제, 무엇을 예약/취소했는가)를 원본 테이블과 분리**해서 남기는 패턴입니다. 실무에서 "이력 테이블 분리"는 매우 흔한 패턴입니다.
- 30초 이내 적재 요구는 사실 DynamoDB Streams + Lambda 조합이면 기본적으로 수 초 내에 처리되므로, 폴링 주기/배치 크기를 극단적으로 이상하게 설정하지만 않으면 자연히 만족됩니다.

### 4) EC2 위의 Flask 앱
- 이 앱은 위에서 설계한 테이블/GSI/조건부쓰기 로직을 실제로 구현하는 애플리케이션 계층입니다.
- 핵심은 **IAM Role을 EC2에 붙여서** (Access Key 하드코딩 금지) DynamoDB에 최소 권한(GetItem/PutItem/UpdateItem/Query 등)만 부여하는 것 — 문제의 "최소 권한 원칙" 유의사항과 직결됩니다.

**한 줄 요약**: 이 모듈은 "동시성 제어(Conditional Write) + 이벤트 기반 후처리(Streams→Lambda) + Sparse GSI"라는 DynamoDB의 3대 핵심 패턴을 하나의 시나리오에 녹인 것입니다.

## 모듈 2. CDN Function — "코드 재배포 없이 실시간으로 트래픽을 나누려면?"

### 이 모듈이 테스트하려는 것
CloudFront의 **엣지 컴퓨팅(CloudFront Functions)**과 **엣지 데이터 저장소(KeyValueStore)**를 이용해서, 오리진(S3)까지 가지 않고도 CDN 엣지에서 요청을 가공하는 능력입니다.

### 1) 왜 S3를 직접 노출하지 않고 CloudFront + OAC로 감싸는가
- S3를 퍼블릭으로 열면 CDN을 우회해서 직접 접근할 수 있어 캐싱/보안 정책이 무력화됩니다.
- **OAC(Origin Access Control)**를 쓰면 "이 CloudFront Distribution을 통해서만" S3에 접근 가능하게 만들 수 있습니다 (S3 Block Public Access 전체 활성화 + Bucket Policy에 CloudFront 서비스 프린시펄만 허용).

### 2) KeyValueStore — "코드 재배포 없이 즉시 반영"의 비밀
- CloudFront Function 코드 자체에 weight(0.3) 값을 박아두면, 비율을 바꿀 때마다 함수를 재배포해야 합니다.
- KVS(엣지에 복제되는 key-value 저장소)에 설정값을 분리해두면, **함수 코드는 그대로 두고 KVS 값만 바꿔서** 즉시 반영할 수 있습니다 — 이게 "설정과 로직의 분리"라는 소프트웨어 설계 원칙이 CDN 레벨에 적용된 사례입니다.

### 3) viewer-request / viewer-response 두 함수가 하는 일 (흐름을 그려보면)

```
[사용자 요청]
   │ Cookie: x-sp-ab=a (있을 수도, 없을 수도)
   ▼
[viewer-request 함수]
   ├─ 쿠키 있음 → 그 값(a/b) 그대로 사용
   ├─ 쿠키 없음 → KVS의 weight 읽고 랜덤값 비교해서 a 또는 b 결정
   ├─ KVS에서 해당 버전의 실제 경로(version_a/version_b) 읽음
   ├─ Request URI를 그 경로로 재작성 (예: / → /version-a/index.html)
   └─ 헤더 x-sp-ab-assigned = 할당된 버전(a/b) 세팅 (다음 단계 전달용)
   ▼
[캐시 조회/오리진(S3) 요청]
   ▼
[viewer-response 함수]
   └─ x-sp-ab-assigned 헤더가 있으면 → Set-Cookie: x-sp-ab=값 추가
   ▼
[사용자에게 응답] (다음부터는 쿠키로 버전 고정됨)
```

- "재접속 시에도 동일 버전 유지"가 되는 이유: 첫 방문 때 Set-Cookie로 브라우저에 버전을 저장해두고, 다음 요청부터는 그 쿠키를 viewer-request가 읽어서 항상 같은 버전으로 보내주기 때문입니다.
- request 헤더는 원래 클라이언트→오리진 방향 요청에만 붙는 건데, 이걸 response 단계까지 "전달"하는 트릭이 바로 `x-sp-ab-assigned` 커스텀 헤더입니다. viewer-request에서 세팅한 헤더는 오리진까지 갔다가 그대로 response 흐름에 남아있어서 viewer-response에서 읽을 수 있습니다.

### 4) Cache Policy — 왜 쿠키를 캐시 키에 포함해야 하는가
- CloudFront는 기본적으로 같은 URL이면 같은 캐시를 씁니다.
- 그런데 지금은 URI 자체를 함수가 재작성하므로 사실 URL은 달라지지만(예: /version-a/index.html vs /version-b/index.html), 안전하게 캐시가 섞이지 않도록 **`x-sp-ab` 쿠키를 캐시 키에 포함**시켜서 A/B 버전별로 완전히 별개의 캐시 엔트리를 갖게 만드는 것입니다.

**한 줄 요약**: 이 모듈은 "엣지에서 로직 실행(Functions) + 엣지에서 설정 참조(KVS) + 상태 유지(Cookie) + 캐시 분리(Cache Policy)"라는 CDN 기반 A/B 테스팅의 표준 패턴입니다.

## 모듈 3. EKS Scaling — "트래픽 폭증 시 Pod도, 노드도 자동으로 늘어나게"

### 이 모듈이 테스트하려는 것
쿠버네티스 오토스케일링은 **2단계**로 이루어진다는 걸 이해하는 게 핵심입니다.
1. **Pod 스케일링** (일이 늘면 일꾼 수를 늘림) — 여기선 KEDA가 담당
2. **Node 스케일링** (일꾼을 놓을 자리가 없으면 자리 자체를 늘림) — 여기선 Karpenter가 담당

이 둘은 별개의 문제이고, 이 과제는 둘을 체인처럼 연결하는 걸 요구합니다.

### 1) 왜 HPA(CPU 기반)가 아니라 KEDA(SQS 기반)인가
- 이 시스템은 SQS 큐에 쌓인 "주문 메시지 수"가 실제 부하 지표입니다. CPU 사용률은 메시지가 쌓여도 당장 안 오를 수 있습니다(컨슈머가 아직 처리를 안 시작했으므로).
- KEDA는 **외부 메트릭 소스(SQS 큐 길이 등)**를 기반으로 스케일링할 수 있게 해주는 애드온입니다. "Pod 1개당 메시지 5건 처리"라는 목표를 설정하면, KEDA가 `(큐에 쌓인 메시지 수) / 5`를 계산해서 필요한 Pod 수를 산출합니다.
- 메시지가 0건이면 Pod를 1개로 축소 — 완전히 0으로 안 줄이는 이유는 "Consumer가 아예 없으면 새 메시지가 와도 처리 시작이 늦어지기 때문" (Cold start 방지 목적의 최소 replica).

### 2) 왜 Cluster Autoscaler가 아니라 Karpenter인가
- 기존 Cluster Autoscaler는 "정해진 NodeGroup(ASG)"의 크기를 늘리는 방식이라 유연성이 떨어집니다.
- **Karpenter**는 Pending 상태의 Pod(자리가 없어서 스케줄 안 된 Pod)를 직접 감지해서, 그 Pod가 필요로 하는 스펙에 맞는 **인스턴스를 바로 골라서 프로비저닝**합니다. 훨씬 빠르고 유연합니다.
- **NodePool/NodeClass**는 Karpenter가 "어떤 종류의 노드를 만들지"에 대한 설계도입니다 (허용 인스턴스 타입, taint, consolidation 정책 등).

### 3) Taint / Toleration — 왜 Addon용 노드와 App용 노드를 분리하는가
```
skm-cluster-addon-ng (고정 1대, t3.medium)  →  taint 적용
   └─ KEDA, Karpenter 같은 "클러스터 운영에 필수인 시스템 컴포넌트"만 여기서 실행

skm-app-nodepool (Karpenter가 자동 생성/삭제)
   └─ order-processor(App)와 DaemonSet만 여기서 실행
```
- 이유: App이 스케일 인/아웃 될 때 Addon 노드까지 같이 흔들리면, KEDA/Karpenter 자체가 죽어버려서 스케일링 시스템 전체가 마비될 수 있습니다. **"스케일링을 담당하는 인프라"와 "스케일링 당하는 대상"을 물리적으로 분리**하는 게 안정성의 핵심입니다.
- Taint를 걸면 기본적으로 아무 Pod도 그 노드에 못 들어갑니다. Addon Pod(KEDA, Karpenter)에는 그 taint를 견디는 toleration을 줘서 예외적으로 배치되게 합니다. App은 반대로 `skm-app-nodepool`에만 배치되도록 nodeSelector/affinity를 걸어줍니다.

### 4) 전체 흐름 정리
```
주문 급증 → SQS 큐에 메시지 쌓임
   → KEDA가 큐 길이 감지 → order-processor Pod 수를 늘림 (최대 5개)
   → 기존 노드 1대로 Pod 5개를 다 못 올림 → Pod가 Pending 상태
   → Karpenter가 Pending Pod 감지 → skm-app-nodepool 스펙대로 새 노드 추가 프로비저닝
   → Pod들이 새 노드에 스케줄됨
   → 큐가 비워짐 → KEDA가 Pod를 1개로 축소
   → 노드 활용도 낮아짐 → Karpenter가 60초 후 여분 노드 회수(Consolidation)
```

**한 줄 요약**: "무엇이 부하 신호인가(SQS) → 그 신호로 Pod를 늘리는 자(KEDA) → Pod 배치 공간이 부족할 때 노드를 늘리는 자(Karpenter)"의 3단 체인이 이 모듈의 전부입니다.

## 모듈 4. Container Logging — "흩어진 Pod 로그를 어떻게 한곳에서 검색 가능하게 만드는가"

### 이 모듈이 테스트하려는 것
쿠버네티스에서 로그를 다루는 표준 파이프라인, 즉 **수집(Collect) → 가공/보강(Enrich) → 저장(Store) → 조회/시각화(Visualize)**의 4단계 구조를 정확히 구현하는 것입니다.

### 전체 파이프라인 그림
```
[log-generator Pod] (stdout에 JSON 로그 출력)
        │  컨테이너 stdout은 노드의 /var/log/pods/*/*/*.log 파일로 자동 기록됨(쿠버네티스 기본 동작)
        ▼
[o11y-otel] (DaemonSet, 모든 노드에 1개씩 실행)
   - filelog receiver: 그 로그 파일들을 읽음
   - k8sattributes processor: "이 로그가 어느 namespace/pod에서 나왔는지" 메타데이터를 붙임
   - OTLP HTTP exporter: 가공된 로그를 Loki로 전송
        ▼
[o11y-loki] (Single Binary, monitoring 네임스페이스, ClusterIP)
   - OTLP Ingestion Endpoint로 로그 수신
   - Chunks/Index를 PV(영구 볼륨)에 저장 → Pod 재시작해도 로그 안 날아감
   - namespace, pod 라벨로 필터링 가능 (k8sattributes가 붙여준 메타데이터 덕분)
        ▼
[o11y-grafana] (ALB로 외부 노출)
   - Loki를 Datasource로 등록
   - LogQL 쿼리로 대시보드 패널 구성 (bar chart / pie chart / logs)
```

### 왜 DaemonSet인가 (Deployment가 아니라)
- 로그는 "각 노드에 있는" 파일을 읽어야 합니다. 즉, **모든 노드마다 반드시 1개씩** 떠 있어야 하는 성격의 워크로드입니다. Deployment는 몇 개를 어디에 띄울지 스케줄러가 자유롭게 정하지만, DaemonSet은 "노드당 정확히 1개"를 보장합니다 — 그래서 로그 수집기, 모니터링 에이전트는 거의 항상 DaemonSet입니다.

### k8sattributes processor가 하는 일
- 원본 로그 파일 경로(`/var/log/pods/<namespace>_<pod-name>_<uid>/...`)에는 이미 namespace/pod 이름 정보가 들어있긴 하지만, 이건 "문자열"일 뿐입니다.
- k8sattributes processor는 쿠버네티스 API와 통신해서 이 정보를 **구조화된 라벨(namespace, pod, container 등)**로 로그에 붙여줍니다. 이 라벨이 있어야 Loki/Grafana에서 `{namespace="o11y", pod="log-generator-xxx"}` 같은 LogQL 필터링이 가능해집니다.

### 왜 Loki는 Single Binary + PV인가
- Loki는 "Index(어디에 뭐가 있는지 찾는 목차)"와 "Chunks(실제 로그 압축 데이터)"를 나눠서 관리합니다.
- Single Binary 모드는 모든 컴포넌트(distributor, ingester, querier 등)를 하나의 프로세스로 실행하는 소규모/테스트용 배포 방식입니다 (실무 대규모는 마이크로서비스 모드로 분리).
- Pod가 재시작되면 컨테이너 내부 디스크는 초기화되므로, Index/Chunks를 **PV(Persistent Volume)**에 저장해야 로그 데이터가 유지됩니다.

### Grafana 대시보드 3종 패널의 의미
- **Log Count Over Time (bar chart)**: 시간대별 로그 발생량 추이 → LogQL의 `count_over_time()` 같은 집계 쿼리로 만듭니다.
- **Log Level Distribution (pie chart)**: info/warn/error 비율 → level 라벨/필드로 group by
- **Recent Logs (logs 패널)**: 원본 로그 스트림을 그대로 최신순으로 보여주는 패널
- 범례가 "대소문자 구분 없이 error/warn/info로 plain text 출력"되어야 한다는 조건은, 로그 원본이 `"level": "INFO"`(대문자)로 오더라도 LogQL에서 소문자로 정규화하거나 패널 표시 옵션을 맞춰야 한다는 뜻입니다.

**한 줄 요약**: "노드 로그 파일 → DaemonSet이 수집·메타데이터 보강 → Loki가 영구 저장 → Grafana가 쿼리·시각화"라는, PLG(Promtail/Loki/Grafana) 스택의 표준 흐름을 OTel Collector로 대체 구현한 것입니다.

## 4개 모듈을 관통하는 공통 사고방식

이 과제 전체를 관통하는 설계 철학은 결국 다음 몇 가지로 압축됩니다.

1. **관심사의 분리**: 원본 데이터/이력 데이터 분리(감사 테이블), 로직/설정 분리(KVS), 시스템 인프라/워크로드 분리(taint), 수집/저장/시각화 분리(OTel/Loki/Grafana)
2. **이벤트 기반 아키텍처**: DynamoDB Streams→Lambda, SQS→KEDA처럼 "무언가 바뀌면 자동으로 다음 동작이 트리거"되는 패턴이 반복됩니다.
3. **최소 권한 & 격리**: IAM 최소 권한, OAC로 S3 직접 접근 차단, 노드 taint로 워크로드 격리 — 전부 "필요한 것만 허용"하는 사고방식입니다.
4. **상태 없는(재배포 없는) 설정 변경**: KVS, Cache Policy처럼 "코드를 안 건드리고 값만 바꿔서 동작을 바꾸는" 구조를 선호합니다.

이 프레임으로 각 모듈을 보면, 세부 스펙(이름, 포트 번호 등)은 암기 대상이지만 **"왜 이 컴포넌트가 필요한가"는 이해로 커버**가 가능합니다. 실전에서 막히면 "지금 이 요구사항이 위 4가지 원칙 중 어디에 해당하는가"를 먼저 따져보시면 접근이 훨씬 수월할 겁니다.
