# 제2과제 vf — 리소스별 이론 완전 설명 (NoSQL / CDN Function / EKS Scaling / Container Logging)

문제에 등장하는 모든 리소스를 이름 그대로 짚어가며, **각 리소스가 정확히 무슨 역할을 하는지, 왜 그 스펙이어야 하는지, 이웃 리소스와 어떻게 연결되는지**를 이론적으로 설명합니다.

# 모듈 1. NoSQL

## bigbae-nosql-reservation-table (DynamoDB 테이블)
- **Partition Key `train_id` + Sort Key `seat_id`의 이론적 의미**: DynamoDB는 아이템을 Partition Key의 해시값으로 여러 파티션(물리적 저장 단위)에 분산 저장합니다. 같은 `train_id`를 가진 아이템들은 같은 파티션(또는 인접 파티션) 내에서 `seat_id` 순으로 정렬되어 저장됩니다. 이 설계 덕분에 "이 기차의 모든 좌석 조회"가 하나의 파티션 내 Query로 효율적으로 처리됩니다. 반대로 Partition Key가 너무 적은 값(예: 기차 종류만 10개)만 가지면 파티션 분산이 안 되어 핫파티션 문제가 생길 수 있는데, 여기선 기차 편수가 충분히 많다는 전제로 설계된 것입니다.
- **Billing Mode PAY_PER_REQUEST**: 미리 처리량(RCU/WCU)을 프로비저닝하지 않고 요청량에 따라 자동 과금·자동 확장되는 모드입니다. 좌석 예약처럼 특정 시간대(오픈런)에 트래픽이 폭증하는 워크로드에서, 사전 용량 설정 실패로 인한 쓰로틀링 위험을 없애기 위한 선택입니다.
- **Stream NEW_AND_OLD_IMAGES**: DynamoDB Streams는 변경 로그를 최대 24시간 보관하는 버퍼입니다. `NEW_AND_OLD_IMAGES`를 선택하면 변경 전/후 아이템 전체가 스트림 레코드에 함께 담기므로, "무엇이 어떻게 바뀌었는지"(예: 취소 시 누가 취소했는지)를 old image에서 알아낼 수 있습니다. `KEYS_ONLY`나 `NEW_IMAGE`만으로는 이 정보를 잃어버립니다.
- **삭제 방지(Deletion Protection)와 PITR**: PITR은 최근 35일 내 임의 시점으로 테이블을 복원할 수 있게 해주는 연속 백업 기능으로, "실수로 잘못된 값을 덮어썼을 때" 같은 논리적 오류로부터 데이터를 보호합니다. 실물 예매 데이터처럼 손실이 치명적인 데이터에 필수로 적용되는 조합입니다.

## gsi-user-reservations (Global Secondary Index)
- **왜 메인 테이블만으로는 부족한가**: 메인 테이블의 Partition Key가 `train_id`이므로, "이 사용자가 예약한 모든 좌석"을 조회하려면 테이블 전체를 Scan해야 합니다(매우 비효율). GSI는 **동일 데이터를 다른 키 구조로 재색인**한 별도의 조회 경로를 제공합니다.
- **PK `user_id` + SK `reserved_at`**: 사용자별로 파티셔닝되고, 예약 시각 순으로 정렬되므로 "이 사용자의 예약 내역을 최신순으로" 조회가 자연스럽게 가능합니다.
- **Sparse Index라는 이론적 성질**: GSI는 원본 아이템에 GSI의 키 속성이 모두 존재할 때만 그 아이템을 인덱스에 포함시킵니다. 즉 좌석이 "available" 상태라 `user_id`/`reserved_at` 속성 자체가 아이템에 없다면, 그 좌석은 애초에 GSI에 나타나지 않습니다. 이 성질을 이용해 "예약된 좌석만 GSI에 노출"시키는 요구사항이 별도 필터링 로직 없이 자연스럽게 구현됩니다. 취소 시에도 `status`만 바꾸는 게 아니라 `user_id`/`reserved_at` 속성 자체를 제거해야, 다음 GSI 갱신 시점에 그 아이템이 인덱스에서 빠집니다.
- **Projection ALL**: GSI에 원본 아이템의 모든 속성을 복제해서 저장하는 방식입니다. 이렇게 하면 GSI만 조회해도 메인 테이블로 재조회(Fetch)할 필요가 없어 지연시간이 줄지만, 저장 공간과 쓰기 비용이 늘어나는 트레이드오프가 있습니다. 조회 응답에 필요한 필드가 많을 때 선택하는 방식입니다.

## bigbae-nosql-audit-table (감사 테이블)
- **PK만 존재(`event_id`)**: 이 테이블은 "이벤트 로그"를 순수하게 나열하는 성격이라 복합 조회 패턴이 필요 없고, 각 이벤트를 고유하게 식별할 단일 키만 있으면 충분합니다. 원본 예약 테이블과 물리적으로 분리해서, 예약 테이블은 "현재 상태"만 관리하고 감사 테이블은 "이력 전체"를 관리하는 책임 분리(CQRS와 유사한 발상)입니다.

## bigbae-nosql-reservation-audit (Lambda 함수)
- **DynamoDB Streams를 트리거로 하는 이벤트 소스 매핑**: Lambda는 스트림을 폴링하며 새 레코드가 생기면 자동으로 실행됩니다. 이는 "누가 DB를 바꿨는지" 애플리케이션 코드가 명시적으로 알릴 필요 없이, DB 변경 자체가 후속 처리를 자동으로 유발하는 **Change Data Capture(CDC)** 패턴의 전형입니다. 원본 API 서버(EC2)는 감사 로직을 전혀 몰라도 되므로 관심사가 완전히 분리됩니다.
- **Timeout 30초의 의미**: Lambda 실행이 이 시간을 넘으면 강제 종료됩니다. "30초 내 적재"라는 SLA 요구사항과 Lambda의 최대 실행시간 제약이 자연스럽게 맞물려 있는데, 실제로 DynamoDB Streams→Lambda 파이프라인은 보통 수 초 내에 처리되므로 타임아웃은 넉넉한 안전마진 역할을 합니다.

## bigbae-nosql-app-ec2 (Flask 애플리케이션 서버)
- 이 EC2는 클라이언트 요청을 받아 위에서 설명한 Conditional Write 로직(조건부 갱신)을 실제로 수행하는 계층입니다. **DynamoDB의 ConditionExpression**은 "현재 저장된 값이 조건을 만족할 때만 쓰기를 허용하고, 그렇지 않으면 원자적으로 실패시키는" 기능으로, 이게 바로 "동시에 여러 요청이 와도 하나만 성공"하는 동시성 제어의 핵심 메커니즘입니다. RDB의 Row Lock 없이도 DynamoDB 단일 아이템 단위의 원자성(Atomicity)만으로 이 문제를 해결할 수 있다는 게 이 설계의 이론적 핵심입니다.
- **Public IP + TCP 8080**: EC2가 Public Subnet에 배치되고 Public IP를 할당받아, 외부에서 직접 이 애플리케이션으로 요청을 보낼 수 있는 구조입니다. 실제 서비스라면 앞단에 ALB를 두는 게 일반적이지만, 이 과제는 단순화를 위해 EC2를 직접 노출합니다.
- **IAM Instance Profile의 역할**: EC2에 붙는 IAM Role은 DynamoDB에 대한 최소 권한(GetItem/PutItem/UpdateItem/Query, 그리고 GSI 인덱스 ARN에 대한 Query 권한)만 가져야 합니다. Access Key를 코드에 넣지 않고 IAM Role을 통해 임시 자격증명을 자동 발급받는 것이 EC2에서 AWS 서비스에 접근하는 표준 방식입니다.

# 모듈 2. CDN Function

## skillsphone-landing-ab-<ACCOUNT_ID> (S3 버킷)
- 정적 파일(index_a.html, index_b.html)의 원본 저장소입니다. 이 버킷은 **모든 Public Access가 차단**되어, S3 URL로 직접 접근하면 반드시 실패해야 합니다. "콘텐츠 서빙의 유일한 경로는 CloudFront"라는 원칙을 지키기 위한 전제 조건입니다.

## OAC (Origin Access Control)
- CloudFront가 S3 Origin에 접근할 때 **SigV4 서명 요청**을 자동으로 붙여주는 메커니즘입니다. S3 Bucket Policy에서 "이 서명이 특정 CloudFront Distribution ARN에서 온 것"만 허용하도록 조건을 걸면, 그 Distribution을 통하지 않은 요청(직접 S3 접근, 다른 CloudFront 등)은 전부 거부됩니다. 예전 방식인 OAI(Origin Access Identity)보다 세밀한 리소스 단위 제어와 SSE-KMS 지원이 가능한 최신 방식입니다.

## skillsphone-cdn-ab-config (CloudFront KeyValueStore)
- CloudFront **엣지 위치(전 세계 POP)마다 복제되는 저지연 Key-Value 저장소**입니다. CloudFront Function은 요청을 처리하는 그 순간(밀리초 단위) 이 KVS에서 값을 읽어올 수 있는데, 이게 가능한 이유는 KVS가 함수와 물리적으로 같은 엣지에 미리 복제되어 있기 때문입니다(네트워크 왕복 없이 로컬 조회).
- **weight, version_a, version_b라는 세 개의 키**: 이 값들은 "함수의 동작 방식을 결정하는 설정"이지 "함수 코드 자체"가 아닙니다. 함수 코드는 "KVS에서 weight를 읽어 랜덤값과 비교한다"는 로직만 담고, 실제 숫자(0.3)는 KVS에만 존재합니다. 그래서 비율을 바꾸고 싶을 때 함수를 재배포(발행)할 필요 없이 KVS 값만 갱신하면 즉시 반영됩니다 — 이게 "설정과 로직의 분리"라는 소프트웨어 설계 원칙이 CDN 엣지 레벨에 구현된 사례입니다.

## skillsphone-cdn-ab-req-fn (viewer-request 함수)
- CloudFront의 **viewer-request 이벤트 타입**은 "CloudFront가 사용자로부터 요청을 받은 직후, 캐시를 조회하기 전" 시점에 실행됩니다. 이 시점에 개입하면 캐시 조회 자체에 영향을 줄 수 있습니다(요청 URI를 바꾸면 다른 캐시 키로 조회됨).
- **cloudfront-js-2.0 런타임과 KVS 연결**: 이 런타임 버전부터 KVS를 참조하는 비동기 API(`cf.kvs()`)가 지원됩니다. 함수를 KVS와 연결(Associate)해야만 함수 코드 내에서 그 KVS를 조회할 수 있습니다 — 이 연결이 없으면 KVS 데이터에 접근 자체가 불가능합니다.
- **역할의 핵심**: (1) 쿠키 유무 확인 → 없으면 weight 기반 랜덤 할당, (2) 할당된 버전에 따라 요청 URI를 실제 파일 경로로 재작성, (3) 다음 단계(viewer-response)로 "이번에 어떤 버전이 할당됐는지"를 전달하기 위해 커스텀 요청 헤더(`x-sp-ab-assigned`)에 값을 심어둡니다. 이 헤더는 원래 뜻대로라면 오리진으로 가는 요청에만 의미가 있지만, CloudFront의 요청-응답 처리 파이프라인 특성상 이 값이 이후 response 처리 단계까지 컨텍스트로 남아있어, viewer-response 함수가 이를 읽어낼 수 있습니다.

## skillsphone-cdn-ab-res-fn (viewer-response 함수)
- CloudFront의 **viewer-response 이벤트 타입**은 "오리진 또는 캐시로부터 받은 응답을 사용자에게 돌려주기 직전" 시점에 실행됩니다. 이 시점엔 요청 URI를 못 바꾸지만(이미 처리 끝), 응답 헤더는 자유롭게 추가/수정할 수 있습니다.
- **역할**: viewer-request가 남긴 `x-sp-ab-assigned` 값이 있으면, 그 값을 `Set-Cookie: x-sp-ab=<값>; Path=/; Max-Age=86400` 형태로 응답 헤더에 심습니다. 이 쿠키가 브라우저에 저장되면서, 다음 요청부터는 viewer-request 함수가 "쿠키가 이미 있다"고 판단해 랜덤 할당 대신 그 값을 그대로 재사용 — 이것이 "재접속 시에도 동일 버전 유지"의 실제 메커니즘입니다.

## skillsphone-cdn-ab-cache-policy (Cache Policy)
- CloudFront는 기본적으로 "같은 캐시 키(보통 URL)"에 대해 하나의 캐시 엔트리만 유지합니다. 이 A/B 시스템에서 A/B 버전마다 실제로는 다른 URI(`/version-a/...` vs `/version-b/...`)로 재작성되므로 원칙적으로 캐시가 자동 분리되긴 하지만, **쿠키를 캐시 키에 포함**시키는 이유는 안전장치 성격입니다: 혹시라도 캐시 키 구성이 URI만으로 충분히 안 나뉘는 경계 상황(재작성 타이밍, 정책 우선순위 등)에서도 명시적으로 A/B가 뒤섞이지 않도록 보장하기 위함입니다.
- **Min/Default/Max TTL (0/300/3600초)**: 오리진이 별도 캐시 제어 헤더를 안 보내는 경우 Default TTL(300초)이 적용되고, 오리진이 명시적으로 캐시 제어 헤더를 보내면 그 값이 Min~Max 범위 내에서 우선됩니다. Min TTL 0은 "오리진이 캐시하지 말라고 하면 그 의사를 존중"하는 하한선 역할입니다.

## Response Headers Policy (커스텀, AWS Managed 미사용)
- 응답에 보안 관련 헤더(X-Content-Type-Options, X-Frame-Options, Strict-Transport-Security 등)를 자동으로 추가하는 정책입니다. AWS Managed Policy를 쓰지 말라는 조건은, "미리 정의된 값이 아니라 이 서비스에 맞는 값을 직접 설계하라"는 최소 구성 원칙의 반영입니다.

## skillsphone-cdn-ab-distribution (CloudFront Distribution)
- 지금까지의 모든 구성요소(S3+OAC, 두 함수, Cache Policy, Response Headers Policy)를 하나로 묶어 실제 서비스 엔드포인트를 만드는 최상위 리소스입니다. **Pay-as-you-go 요금제**는 사용한 만큼만 과금되는 기본 CloudFront 요금 방식으로, 별도 커밋(Savings Bundle) 없이 구성한다는 뜻입니다.

# 모듈 3. EKS Scaling

## skm-order-queue (SQS Standard Queue)
- **Standard Queue의 특성**: 최소 한 번(At-least-once) 전달을 보장하지만 순서는 보장하지 않고, 처리량 제한도 사실상 없습니다(FIFO Queue는 반대로 순서를 보장하지만 처리량이 제한적). 주문 처리처럼 "순서는 크게 중요하지 않지만 대량 처리량이 필요한" 워크로드에 적합합니다.
- **KEDA가 이 큐를 참조하는 방식**: KEDA는 SQS의 `ApproximateNumberOfMessages` 지표를 주기적으로 폴링해서, 이 값을 Kubernetes의 커스텀 메트릭처럼 다뤄 HPA(Horizontal Pod Autoscaler)를 대신 제어합니다(정확히는 KEDA가 내부적으로 HPA 리소스를 생성/관리).

## skm-eks-cluster (EKS 클러스터)
- 쿠버네티스의 **Control Plane**(API Server, etcd, Scheduler, Controller Manager)을 AWS가 완전관리형으로 운영해주는 서비스입니다. 사용자는 Control Plane의 가용성/패치는 신경 쓰지 않고, Worker Node(Data Plane)만 관리하면 됩니다.

## skm-cluster-addon-ng (Addon NodeGroup)
- **Managed NodeGroup**: EC2 인스턴스의 프로비저닝/교체/롤링업데이트를 AWS가 자동화해주는 노드 그룹 형태입니다.
- **Desired/Min/Max 1/1/1의 의미**: 이 노드그룹은 고정 크기이며 스케일링 대상이 아닙니다 — "시스템 컴포넌트를 위한 안정적이고 예측 가능한 기반"이라는 역할에 맞게, 여기는 오토스케일링을 걸지 않습니다.
- **Taint의 이론**: Taint는 노드에 "이 노드는 특별한 조건 없이는 아무 Pod도 못 들어온다"는 배타적 표시를 남기는 것이고, Toleration은 특정 Pod가 "나는 이 taint를 견딜 수 있다"고 선언하는 대응 개념입니다. KEDA와 Karpenter 같은 시스템 컴포넌트에만 이 Toleration을 부여해, App이 실수로라도 이 안정적인 노드그룹에 배치되지 않도록 원천 차단합니다. 이렇게 분리하는 이유는, App이 스케일 인/아웃 되며 노드가 빈번히 생성/삭제될 때 시스템 컴포넌트까지 같이 흔들리면 스케일링 시스템 자체가 불안정해지기 때문입니다.

## KEDA (keda 네임스페이스)
- KEDA는 Kubernetes의 표준 오토스케일러(HPA)가 CPU/메모리 같은 리소스 메트릭만 다루는 한계를 넘어, **외부 이벤트 소스(SQS 큐 길이, Kafka Lag 등) 기반 스케일링**을 가능하게 하는 애드온입니다. 내부적으로 "Scaler"라는 플러그인 아키텍처로 다양한 소스를 지원합니다.

## order-scaler (ScaledObject, skillsmkt 네임스페이스)
- ScaledObject는 KEDA가 "무엇을(Deployment) 어떤 지표로(SQS 큐 길이) 어떻게(Min/Max Replica) 스케일링할지"를 선언하는 커스텀 리소스입니다.
- **queueLength 5, Min 1 / Max 5의 이론**: KEDA는 대략 `필요 Pod 수 = ceil(현재 큐 메시지 수 / queueLength)` 공식으로 목표 Replica 수를 계산합니다. Min을 1로 두는 이유는, 메시지가 0건이 되어도 Pod를 완전히 0으로 줄이면 다음 메시지가 왔을 때 Pod가 새로 뜨는 Cold Start 지연이 발생하기 때문에, 최소한의 상시 대기 Pod를 유지하는 정책입니다.

## Karpenter (kube-system 네임스페이스)
- 기존 Cluster Autoscaler는 "미리 정의된 ASG(Auto Scaling Group)의 크기"만 조절할 수 있는 한계가 있는 반면, Karpenter는 **Pending 상태의 Pod(스케줄링되지 못한 Pod)를 직접 감시**하다가, 그 Pod가 요구하는 리소스 스펙에 맞는 인스턴스를 **그때그때 동적으로 선택**해서 프로비저닝합니다. "미리 정해진 노드 유형의 개수를 늘리는" 방식이 아니라 "필요에 맞는 노드를 즉석에서 만드는" 방식이라는 게 근본적 차이입니다.

## skm-app-nodepool / skm-app-nodeclass (Karpenter NodePool / EC2NodeClass)
- **EC2NodeClass**: Karpenter가 만들 노드의 AWS 레벨 스펙(AMI, 서브넷, 보안그룹, IAM Role 등)을 정의하는 설계도입니다.
- **NodePool**: 어떤 EC2NodeClass를 쓸지, 어떤 인스턴스 타입(t3.small, t3.medium)을 허용할지, 어떤 라벨/taint를 노드에 부여할지, 그리고 **Consolidation 정책**(유휴/저활용 노드를 언제 회수할지)을 정의합니다. "60초 후 반환"이라는 조건은 이 Consolidation 정책의 대기 시간으로 구현됩니다.
- **Taint를 이 NodePool에도 거는 이유**: App/DaemonSet 외의 워크로드가 실행되지 않아야 한다는 요구사항을 지키기 위해, 이 NodePool이 만드는 모든 노드에도 taint를 걸고, App Deployment 쪽에 그 Toleration을 부여합니다.

## order-processor (Deployment, skillsmkt 네임스페이스)
- CPU 500m/Memory 512Mi Request는 스케줄러가 "이 Pod가 최소 이 정도 자원은 확보되어야 배치 가능하다"고 판단하는 기준값이며, Karpenter는 Pending Pod의 이 Request 값을 보고 어떤 크기의 인스턴스가 필요한지 역산합니다.
- **nodeSelector로 skm-app-nodepool만 지정**: 이 Pod가 Addon NodeGroup이나 다른 노드풀에 잘못 배치되지 않도록, Karpenter가 부여한 노드 라벨을 정확히 지정합니다.

# 모듈 4. Container Logging

## o11y-cluster (EKS 클러스터, Multi-AZ NodeGroup)
- **Multi-AZ 배치의 의미**: NodeGroup이 여러 AZ에 걸친 서브넷을 사용하도록 구성하면, EKS는 노드를 여러 AZ에 고르게 분산 생성합니다. 한 AZ 장애가 나도 다른 AZ의 노드/Pod가 살아있어 로깅 파이프라인 전체가 죽지 않습니다.
- **TimeZone KST 설정**: 로그의 타임스탬프를 사람이 보기 편한 현지 시간대로 통일하기 위한 설정으로, 보통 NodeGroup의 Launch Template(User Data)에서 `timedatectl set-timezone Asia/Seoul` 같은 방식으로 적용됩니다.

## log-generator (Deployment, o11y 네임스페이스)
- 애플리케이션이 **stdout으로 JSON 로그를 출력**하는 것 자체가 컨테이너 로깅의 표준 관행(12-Factor App의 "로그는 이벤트 스트림으로 취급하라" 원칙)입니다. 컨테이너 런타임(containerd)이 이 stdout을 자동으로 노드의 파일 시스템(`/var/log/pods/...`)에 기록해주므로, 애플리케이션이 직접 파일 I/O를 다룰 필요가 없습니다.

## o11y-app-alb / o11y-app-tg
- ALB가 log-generator Pod들을 Target Group으로 묶어 외부 트래픽을 분산합니다. 이 앱을 향한 HTTP 요청이 결국 로그를 발생시키는 원천(Log Producer) 역할을 합니다.

## o11y-otel (DaemonSet, monitoring 네임스페이스)
- **DaemonSet의 이론적 필연성**: 로그는 "그 로그를 발생시킨 컨테이너가 있는 바로 그 노드"의 파일 시스템에 있습니다. 즉 수집기는 반드시 각 노드마다 존재해야만 그 노드의 로그에 접근할 수 있습니다. DaemonSet은 쿠버네티스가 "클러스터의 모든(또는 조건에 맞는) 노드에 정확히 1개씩" Pod를 보장하는 워크로드 타입이라, 로그/모니터링 에이전트에 거의 항상 쓰입니다.
- **filelog Receiver**: OTel Collector의 컴포넌트 중 하나로, 지정된 경로(`/var/log/pods/*/*/*.log`)의 파일을 tail(꼬리 읽기)하며 새로 추가되는 로그 라인을 실시간으로 읽어들입니다.
- **k8sattributes Processor**: 원본 로그 파일 경로 문자열(예: `namespace_podname_uid` 형식)만으로는 구조화된 메타데이터가 아닙니다. 이 Processor가 쿠버네티스 API 서버에 질의해서, "이 로그가 정확히 어느 namespace/pod/container에서 나왔는지"를 구조화된 라벨(속성)로 로그 레코드에 덧붙입니다(Enrichment). 이 라벨이 있어야 나중에 Loki/Grafana에서 namespace/pod 단위 필터링이 가능해집니다.
- **OTLP HTTP Exporter**: 가공이 끝난 로그를 표준 프로토콜(OpenTelemetry Protocol, HTTP 방식)로 Loki에 전송하는 출력 컴포넌트입니다.

## o11y-loki (Loki, Release/Service Name)
- **Single Binary 모드**: Loki는 원래 여러 마이크로서비스(distributor, ingester, querier, compactor 등)로 분리 배포하는 게 대규모 운영 방식이지만, Single Binary 모드는 이들을 하나의 프로세스로 합쳐 소규모/테스트 환경에 적합하게 만든 배포 형태입니다.
- **Index와 Chunks**: Loki는 로그 원문을 압축해서 저장하는 Chunks와, "어떤 라벨 조합의 로그가 어느 Chunk에 있는지" 찾아주는 Index를 분리 관리합니다. 이 둘을 Persistent Volume에 저장해야 Pod가 재시작돼도 로그 데이터가 유지됩니다(컨테이너 내부 디스크는 재시작 시 초기화되므로).
- **OTLP Ingestion Endpoint 활성화**: Loki가 OTel Collector로부터 오는 OTLP 형식의 로그를 직접 받아들일 수 있게 하는 설정입니다 — 예전 Loki는 자체 포맷(Promtail push API)만 지원했지만, 최신 버전은 OTLP도 네이티브로 수신 가능합니다.
- **ClusterIP Service**: 클러스터 내부에서만 접근 가능한 서비스 타입으로, Loki는 로그 저장소이지 외부에 직접 노출할 이유가 없으므로 이 타입이 적합합니다. Grafana가 이 내부 주소로 Loki에 질의합니다.

## o11y-grafana (Grafana, monitoring 네임스페이스)
- Loki를 **Datasource**로 등록하면, Grafana는 LogQL(Loki 전용 쿼리 언어)로 로그를 조회해 패널에 표시할 수 있습니다.
- **Log Overview 대시보드의 3개 패널**:
  - Log Count Over Time(bar chart): 시간을 x축으로 구간별 로그 발생 건수를 집계해 막대로 표현 — LogQL의 시간 범위 집계 함수 개념(`count_over_time`)이 이 패널의 데이터 소스가 됩니다.
  - Log Level Distribution(pie chart): 전체 로그를 `level` 필드 값(info/warn/error)으로 그룹핑해 비율을 원그래프로 표현.
  - Recent Logs(logs 패널): 원본 로그 스트림을 최신순으로 나열하는, 가공 없는 로우 로그 뷰.
  - 범례가 "대소문자 구분 없이 plain text"로 나와야 한다는 요구는, 로그 원본의 `level` 값이 대문자(INFO/WARN/ERROR)로 오더라도 시각화 시엔 표기를 통일해서 보여줘야 한다는 뜻입니다.
- **ALB로 외부 노출**: Grafana는 운영자가 접근해야 하는 대시보드이므로 인터넷에서 접근 가능해야 하고, 이를 위해 ALB(Ingress를 통한 AWS Load Balancer Controller 연동)를 앞단에 둡니다.

# 이 과제 전체를 관통하는 핵심 이론 요약

| 이론 개념 | 정의 | 적용 사례 |
|---|---|---|
| 조건부 원자적 쓰기 (Conditional Write) | "현재 상태가 조건을 만족할 때만" 쓰기를 원자적으로 허용/거부 | DynamoDB 좌석 예약 |
| 희소 인덱스 (Sparse Index) | 인덱스 키 속성이 없는 아이템은 인덱스에서 자동 제외됨 | GSI |
| 변경 데이터 캡처 (CDC) | DB의 변경 자체가 후속 이벤트를 자동으로 유발 | DynamoDB Streams → Lambda |
| 설정/로직 분리 | 동작 방식을 결정하는 값을 코드 밖(외부 저장소)에 둠 | KeyValueStore |
| 오리진 접근 제어 | CDN을 거치지 않은 직접 접근을 원천 차단 | OAC |
| 이벤트 기반 오토스케일링 | 리소스 메트릭이 아닌 외부 이벤트 지표로 Pod 수 결정 | KEDA |
| 즉석 노드 프로비저닝 | Pending Pod의 요구사항을 보고 그때그때 맞는 노드를 생성 | Karpenter |
| 노드 배타적 예약 (Taint/Toleration) | 특정 노드에 특정 워크로드만 배치되게 강제 | Addon/App 분리 |
| 노드별 필수 배포 (DaemonSet) | 모든 노드에 정확히 1개씩 배치를 보장 | 로그/메트릭 수집기 |
