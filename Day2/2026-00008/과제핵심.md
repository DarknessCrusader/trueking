## 🗃️ 모듈 1. DocumentDB based NoSQL Application

### `skills-nosql-docdb-cluster` / `skills-nosql-docdb-instance-1`
> **핵심**: Cluster(스토리지) + Instance(컴퓨트) 분리 아키텍처 (Aurora와 동일한 발상)

- Cluster: 여러 AZ에 걸쳐 복제되는 공유 스토리지 관리
- Instance: 그 스토리지에 붙어 쿼리 처리하는 컴퓨트 노드
- 이 분리 덕분에 Instance 추가/제거해도 스토리지 복제는 영향 없음
- `db.t3.medium` = Instance의 컴퓨트 크기(처리량·메모리 결정)

**보안/내구성 스펙**

| 항목 | 값 | 의미 |
|---|---|---|
| Storage Encryption | Enabled + `alias/skills-nosql-docdb` | 디스크 데이터 전체 암호화, **생성 시점에만 지정 가능** |
| TLS | Enabled | 전송 구간 암호화, CA 인증서 없으면 핸드셰이크 자체 실패 |
| Backup Retention | 1일 이상 | 특정 시점 복구(PITR) 가능 범위 |
| 외부 노출 | 금지 | DocumentDB는 원래 VPC 내부 전용 서비스 → Private 배치 + SG로 Client EC2만 허용 |

---

### `skills-nosql-client-ec2` (Flask, docdb_client.py)
> **핵심**: DB는 숨기고 애플리케이션만 노출하는 계층화

- Public IP + TCP 8080으로 외부 요청 수신 → 내부적으로 DocumentDB 쿼리
- 코드 수정 금지 조건 → **환경/인프라만 올바르게 맞추는 게 채점 핵심**

---

### `skills-nosql-docdb-secret` (Secrets Manager)
> **핵심**: Secret은 순수 자격증명만, 연결 로직은 코드가 담당 (책임 분리)

| 키 | 값 | 비고 |
|---|---|---|
| `username` | DB 사용자명 | |
| `password` | DB 비밀번호 | |
| `host` | DocumentDB 엔드포인트 호스트명 | **Scheme(mongodb://)·Port(27017) 미포함** |

- 포트/프로토콜이 바뀌어도 Secret 자체는 안 건드려도 되는 구조
- EC2 IAM Role은 이 Secret ARN에 대한 `GetSecretValue`만 최소 권한으로 부여

---

### `skills_retail` DB — orders / products / sessions
> **핵심**: 왜 DynamoDB 대신 DocumentDB(MongoDB 호환)인가 — 복합 인덱스·범위 쿼리·TTL이 훨씬 유연

**orders 컬렉션**
| 인덱스 | 목적 |
|---|---|
| `{orderId: 1} unique` | 주문 ID 유일성을 DB 레벨에서 강제 |
| `{customerId: 1, createdAt: -1}` | "고객별 최신순 주문" 조회 최적화 |
| `{status: 1, dueAt: 1}` | "특정 상태 + 마감 임박" 운영 쿼리 |

**products 컬렉션**
| 인덱스 | 목적 |
|---|---|
| `{productId: 1} unique` | 상품 ID 유일성 |
| `{warehouseId: 1, stock: 1}` | 창고별 재고 현황 조회 |

**sessions 컬렉션**
| 인덱스 | 목적 |
|---|---|
| `{sessionId: 1} unique` | 세션 ID 유일성 |
| `{expiresAt: 1} TTL expireAfterSeconds:0` | ⭐ 만료 시각 지나면 **자동 삭제** |
| `{customerId: 1, lastSeen: -1}` | 고객별 최근 세션 조회 |

> **TTL 인덱스 주의**: BSON **Date 타입** 필드에만 정상 동작. 문자열로 저장하면 TTL 무시됨.

## 🔗 모듈 2. Simplify Service Networking with VPC Lattice

### `skills-lattice-client-vpc` / `skills-lattice-service-vpc`
> **핵심**: 두 VPC 사이에 Peering/Transit Gateway **직접 연결을 만들지 않음**이 이 모듈의 제약

---

### VPC Lattice 자체의 이론적 위치
> **핵심**: 네트워크 계층(3-4계층) 대신 애플리케이션 계층(7계층)에서 서비스를 연결

- 기존 방식(Peering/TGW): VPC가 늘수록 연결 관리 기하급수적 복잡 (N개면 최대 N(N-1)/2 Peering) + CIDR 충돌
- VPC Lattice: "이 서비스를 이 VPC들에서 쓸 수 있다"는 **서비스 단위 논리적 연결**만 선언
- 실제 트래픽은 AWS가 관리하는 Lattice 데이터 플레인 경유 → 라우팅 테이블/CIDR 신경 안 써도 됨

---

### `skills-lattice-sn` (Service Network)
> **핵심**: "어떤 VPC가 어떤 Service를 쓸 수 있는가"의 상위 컨테이너

- Client VPC를 **Association** → 그 VPC 리소스가 Service Network 안의 Service 호출 가능
- **Association Security Group**: Client VPC CIDR(10.61.0.0/16)만 허용하는 2차 방어선

### `skills-lattice-order-service` (Service)
> **핵심**: 자동 생성 도메인(Generated Domain)으로 호출하는 논리적 엔드포인트

- Client는 이 도메인만 알면 됨 → 실제 라우팅은 Lattice가 처리 (서비스 디스커버리 자동화)
- Service 생성 ≠ Service Network 연결 — **별개 단계이므로 반드시 Association 필요**

### `skills-lattice-order-tg` (Target Group)
> **핵심**: ALB Target Group과 동일 개념 — 백엔드 목록 + Health Check(`/health`)

### `skills-lattice-http-listener` (Listener)
> **핵심**: 포트로 들어온 요청을 Target Group으로 Forward하는 진입점 규칙

---

### Service EC2 Security Group — Managed Prefix List ⭐ 이 모듈의 핵심 이론
> **핵심**: "Lattice를 거친 트래픽만" 정확히 허용 → 우회 접근 원천 차단

- Client가 Service EC2에 접근할 때 실제로는 **Lattice 프록시 IP**에서 오는 것처럼 보임
- SG를 `0.0.0.0/0`으로 열면 "VPC 안 거치고 직접 붙는" 우회 경로가 생겨 Lattice 도입 취지가 깨짐
- → AWS 관리형 **Managed Prefix List**(Lattice 전용 IP 대역)만 소스로 허용

### 응답의 `via=vpc-lattice` 필드
> **핵심**: "실제로 Lattice 경로를 거쳤다"를 증명하는 채점/검증용 마커

## 🛡️ 모듈 3. Cloud Event Handling

> v8 과제의 Event Handling과 이론적으로 동일한 패턴(CloudTrail→EventBridge→Lambda→SNS). 감시 대상을 "SG Inbound 추가" 하나로 좁힌 버전.

### `skills-ceh-protected-sg`
> **핵심**: 이 SG 자체가 "보호 대상" — 최종 제출 시 Inbound 규칙 **0개**가 정상 상태

- 누군가 여기에 규칙을 추가하면 그게 곧 "위반 이벤트"

### `skills-ceh-alert-topic` (SNS, Standard)
> **핵심**: 순서 보장 없는 대신 처리량 제약 적음 — 단발성 알림에 충분

### `skills-ceh-remediate-fn` (Lambda)
> **핵심**: 환경변수 주입으로 "코드는 고정, 대상만 교체 가능"하게 설계

| 환경변수 | 값 |
|---|---|
| `PROTECTED_SECURITY_GROUP_ID` | 보호 대상 SG ID |
| `SNS_TOPIC_ARN` | 알림 Topic ARN |

- 동작 3가지: **자동 복구** / **알림 발행** / **감사 추적(로그)** — 서로 다른 목적의 사이드 이펙트

### `skills-ceh-sg-change-rule` (EventBridge)
> **핵심**: `AuthorizeSecurityGroupIngress`라는 정확한 API 액션명에만 매칭

- EC2 관련 API가 수십 가지인데, 정확히 이 액션에만 반응 → 무관한 호출로 인한 오작동 방지

### `skills-ceh-cloudtrail` (Trail, Logging Enabled)
> **핵심**: 이게 꺼져 있으면 Rule이 아무리 정확해도 감지할 이벤트 자체가 없음

### 180초 이내 자동 복구
> **핵심**: 전체 파이프라인(CloudTrail 기록 → EventBridge 필터링 → Lambda 호출 → 복구)의 누적 지연시간이 짧아야 함을 실전 검증

## 📦 모듈 4. Event-driven Pod Scaling with AWS SQS

### `skills-sqs-cluster` (EKS) + Fargate Profile 2종
> **핵심**: 컨트롤러(KEDA/Karpenter)를 Fargate에 올려 Worker Pod와 완전 물리 격리

| Fargate Profile | Namespace |
|---|---|
| `skills-sqs-fp-keda` | `keda` |
| `skills-sqs-fp-karpenter` | `karpenter` |

- **왜 Fargate인가**: 이 컨트롤러들은 "스케일링 시스템 자체를 운영하는 인프라" → Worker 스케일 인/아웃에 영향받으면 안 됨
- Fargate는 "고정 EC2 노드" 개념이 없어 Worker NodePool과 완전히 물리적으로 분리
- (참고: vf 과제는 taint로 분리했는데, Fargate는 그보다 **한 단계 더 높은 격리도**)

---

### `skills-sqs-queue` (SQS)
> **핵심**: KEDA의 스케일링 지표 원천

- Visibility Timeout(30초 이상) > Worker 처리시간(PROCESSING_SECONDS) → 같은 메시지 중복 처리 방지

---

### IRSA 3종 (Pod Identity)
> **핵심**: 같은 노드 위에 있어도 Pod마다 정확히 필요한 권한만 (Node Role 공유 시 과다 권한 문제 방지)

| ServiceAccount | Namespace | 필요 권한 |
|---|---|---|
| `keda-operator` | `keda` | SQS `GetQueueAttributes` |
| `karpenter` | `karpenter` | EC2 인스턴스 생성/삭제 |
| `sqs-worker-sa` | `skills-sqs` | SQS `ReceiveMessage`/`DeleteMessage` |

---

### `sqs-worker` (Deployment, `skills-sqs`)
> **핵심**: nodeSelector 이중 조건으로 정확한 NodePool에만 배치 강제

```
nodeSelector:
  karpenter.sh/nodepool: skills-sqs-nodepool   ← Karpenter가 시스템적으로 자동 부여
  skills-nodepool: event-worker                ← NodePool 스펙에 정의한 커스텀 라벨
```

- 두 조건을 동시 요구 → 클러스터에 여러 NodePool이 있어도 정확히 이 NodePool 노드에만 배치
- **Fargate 아닌 Karpenter EC2에서 실행돼야 하는 이유**: Fargate는 아직 특정 인스턴스 타입/GPU/커스텀 AMI 같은 세밀 요구를 완전 지원 못함 → 가변적/커스터마이징 필요 워크로드는 Karpenter+EC2가 실무 표준

---

### `sqs-worker-scaledobject` / `sqs-worker-trigger-auth` (KEDA)
> **핵심**: `필요 Pod 수 ≈ ceil(큐 메시지 수 / 2)`, 완전한 이벤트 기반(min=0) 지향

| 설정 | 값 | 의미 |
|---|---|---|
| queueLength | 2 | Pod 1개당 처리 목표 메시지 수 |
| Min / Max | 0 / 6 | 메시지 없으면 Pod **완전히 0** (vf 과제의 min=1과 대비되는 설계 철학) |
| pollingInterval | ≤15초 | 너무 길면 반응 느림 |
| cooldownPeriod | ≤30초 | 너무 짧으면 스케일 인/아웃 떨림(flapping) 발생 |

- `TriggerAuthentication`: KEDA가 SQS API 호출 시 쓸 인증 수단 정의 (Pod Identity 참조)

---

### `skills-sqs-nodepool` / `skills-sqs-nodeclass` (Karpenter)
> **핵심**: 라벨 자동 부여 + Consolidation으로 "종료 시 Pod 1개/Node 1대"에 수렴

- NodePool Label `skills-nodepool=event-worker` → 이 NodePool이 만드는 모든 노드에 자동 부여
- `spec.disruption.consolidationPolicy` → 유휴/저활용 노드 자동 통합·제거 → 부하 감소 후 여분 노드 자동 정리
- Allowed Instance Types(t3.small, t3.medium) → Pending Pod 요구 자원에 맞춰 이 안에서 크기 선택

## 🎯 핵심 이론 요약

| 이론 개념 | 정의 | 적용 사례 |
|---|---|---|
| 스토리지/컴퓨트 분리 아키텍처 | 저장 계층과 쿼리 계층을 독립적으로 확장 | DocumentDB Cluster/Instance |
| 자격증명·연결로직 분리 | Secret은 순수 데이터만, 프로토콜/포트는 코드가 담당 | Secrets Manager `host` |
| TTL 기반 자동 삭제 | 지정 시각 지나면 문서를 백그라운드에서 자동 정리 | `sessions.expiresAt` |
| 애플리케이션 계층 서비스 메시 | 네트워크 안 잇고 서비스 단위로 논리적 연결 | VPC Lattice |
| Managed Prefix List | 특정 AWS 서비스 트래픽만 정확히 식별해 허용 | Lattice 전용 SG 허용 |
| 서버리스 컨트롤 플레인 격리 | 컨트롤러를 Fargate로 분리해 Worker와 완전 격리 | KEDA/Karpenter Fargate |
| Pod 단위 세분화된 IAM | 같은 노드 위에서도 Pod마다 다른 권한 | IRSA |
| Scale-to-Zero | 이벤트 없을 때 컴퓨트 자원을 0으로 | KEDA min=0 |
| 노드 자동 통합/회수 | 저활용 노드를 자동 정리해 비용 최소화 | Karpenter Consolidation |
