# 클라우드컴퓨팅 제2과제 (DocumentDB / VPC Lattice / Event Handling / SQS Pod Scaling) — 개념 이해 가이드

세 번째 버전의 과제지입니다. 지난 두 과제(vf, v8)와 또 다른 4개 모듈이지만, 자세히 보면 **"이전 과제에서 봤던 패턴의 변형"**이 많습니다. 그 연결고리를 짚어가며 설명합니다.

| 모듈 | 리전 | 핵심 주제 | 이전 과제와의 연결 |
|---|---|---|---|
| 1. DocumentDB NoSQL | ap-northeast-2 (서울) | MongoDB 호환 관리형 DB + Secrets Manager | vf의 DynamoDB 모듈과 "NoSQL 데이터 저장" 목적은 같지만 완전히 다른 서비스 |
| 2. VPC Lattice | ap-northeast-1 (도쿄) | 서비스 간 네트워킹 (VPC 경계를 안 넘고 연결) | 완전히 새로운 주제 |
| 3. Cloud Event Handling | ap-southeast-1 (싱가포르) | SG 변경 자동 감지·복구 | v8의 모듈3과 거의 동일한 패턴, 대상만 SG로 좁혀짐 |
| 4. Event-driven Pod Scaling | us-west-2 (오레곤) | SQS+KEDA+Karpenter, Fargate와 EC2 혼합 | vf의 EKS Scaling 모듈과 거의 동일한 패턴 + Fargate 추가 |

## 모듈 1. DocumentDB based NoSQL Application — "관리형 MongoDB로 문서형 데이터를 다루기"

### 이 모듈이 테스트하려는 것
DynamoDB(Key-Value/Wide-Column)와 다르게, **DocumentDB는 MongoDB API 호환 문서형 DB**입니다. "왜 굳이 DynamoDB 대신 DocumentDB를 쓰는가?"를 이해하면 이 모듈의 설계가 자연스럽게 읽힙니다.

### DynamoDB vs DocumentDB — 핵심 차이
- DynamoDB는 스키마리스지만 **키 설계(PK/SK)에 의해 조회 패턴이 제한**됩니다. GSI를 추가로 만들지 않으면 원하는 방식으로 못 찾습니다.
- DocumentDB(MongoDB 호환)는 **복합 인덱스, 배열/중첩 문서, 범위 쿼리, TTL** 등 RDB에 가까운 유연한 쿼리가 가능합니다. 이 과제가 요구하는 `{ status: 1, dueAt: 1 }` 같은 복합 인덱스나 `expireAfterSeconds: 0` TTL 인덱스는 DynamoDB엔 없는 MongoDB 특유의 기능입니다.
- 즉 이 모듈은 "DynamoDB로는 표현하기 까다로운 복잡한 문서/인덱스 구조를 다뤄야 할 때 DocumentDB를 쓴다"는 선택 기준을 보여줍니다.

### 네트워크 구조 — "DB는 절대 외부 노출 금지, App만 노출"
```
[Internet] → [Client EC2 (Public IP, :8080)] → (내부 통신) → [DocumentDB Cluster (외부 노출 금지)]
```
- DocumentDB는 원래도 VPC 내부 전용 서비스라 외부 직접 접근이 원천적으로 불가능합니다(RDS와 비슷). 그래서 "DocumentDB Cluster는 외부 직접 노출 금지"라는 조건은 **Public Subnet에 두지 말고 접근 SG도 Client EC2에서만 열라**는 의미로 이해하면 됩니다.
- Client EC2만 Public IP로 열려있고, 실제 DB 인증정보는 코드에 넣지 않고 **Secrets Manager**에서 가져오는 구조 — "자격증명을 코드/환경변수에 하드코딩하지 않는다"는 보안 원칙의 실전 적용입니다.

### Secrets Manager의 역할 이해하기
- Secret에 `username`, `password`, `host` 세 값을 담아두고, 애플리케이션이 부팅 시점에 Secrets Manager API를 호출해서 이 값을 읽어옵니다.
- `host`에 Scheme(mongodb://)이나 Port(27017)를 포함하지 않는다는 조건이 중요합니다 — Secret은 순수 데이터(호스트명)만 담고, **연결 문자열 조합(Port 27017, TLS 옵션 등)은 애플리케이션 코드에서 처리**하도록 역할이 나뉘어 있는 겁니다. Secret과 애플리케이션 설정의 책임을 분리한 것.
- Client EC2에는 이 Secret을 읽을 수 있는 IAM Role(GetSecretValue 권한)만 최소로 부여해야 합니다.

### TLS와 CA Bundle — 왜 필요한가
- DocumentDB는 기본적으로 TLS 암호화 연결을 요구합니다. `global-bundle.pem`은 AWS가 제공하는 인증서 묶음으로, 클라이언트가 이 CA를 신뢰하도록 pymongo 연결 옵션에 지정해야 TLS 핸드셰이크가 성공합니다 — "전송 중 데이터 암호화"를 강제하는 관리형 서비스의 표준 방식입니다.

### 인덱스 설계 읽는 법
- `{ orderId: 1 } unique`: 정렬 방향(1=오름차순)은 사실 unique 제약에서는 크게 안 중요하지만, 유일성 보장이 핵심 — "같은 orderId가 중복 저장되면 안 된다"는 비즈니스 규칙을 DB 레벨에서 강제.
- `{ customerId: 1, createdAt: -1 }`: "이 고객의 주문을 최신순으로 빠르게 조회"하는 쿼리를 위한 복합 인덱스 — 실무에서 "고객별 주문 내역 최신순 정렬" 화면을 만들 때 반드시 필요한 패턴입니다.
- `{ expiresAt: 1 } TTL expireAfterSeconds: 0`: MongoDB TTL 인덱스는 "이 필드의 시각이 지나면 문서를 자동 삭제"하는 기능입니다. `expireAfterSeconds: 0`은 "expiresAt에 저장된 시각이 되는 순간 바로 삭제"라는 뜻 — 세션 데이터처럼 유효기간이 지나면 자동으로 청소돼야 하는 데이터에 딱 맞는 기능입니다. (DynamoDB의 TTL과 개념은 같지만 MongoDB 쿼리 문법으로 표현된다는 점이 다름)

**한 줄 요약**: "복잡한 쿼리/인덱스가 필요한 문서형 데이터는 DocumentDB, 자격증명은 Secrets Manager로 분리, DB는 절대 외부 비노출"이라는 관리형 문서 DB 운영의 표준 패턴입니다.

## 모듈 2. Simplify Service Networking with VPC Lattice — "VPC를 몰라도 서비스끼리 통신하게 하려면?"

### 이 모듈이 테스트하려는 것
전통적으로 서로 다른 VPC의 서비스가 통신하려면 **VPC Peering이나 Transit Gateway**로 네트워크를 직접 연결해야 했습니다. 이 모듈은 그런 네트워크 레벨 연결 없이 **VPC Lattice라는 애플리케이션 레벨 서비스 메시**로 통신을 단순화하는 게 핵심입니다.

### 왜 굳이 VPC Peering을 안 쓰는가 (문제에서 명시적으로 금지)
- VPC Peering/Transit Gateway는 "네트워크(IP 레벨)"를 직접 연결하는 방식이라, CIDR 겹침 문제, 라우팅 테이블 관리, 보안그룹 상호 참조 등 관리 부담이 큽니다.
- **VPC Lattice**는 VPC 간 네트워크를 직접 잇지 않고, **Service Network라는 논리적 레이어**로 "이 서비스를 쓸 수 있는 VPC들"을 연결합니다. 즉 IP 라우팅이 아니라 "서비스 디스커버리 + 트래픽 라우팅"을 애플리케이션 레벨에서 해결하는 겁니다 — 마이크로서비스가 많아질수록 Peering 개수가 N² 로 늘어나는 문제를 해결하는 게 VPC Lattice의 존재 이유입니다.

### 아키텍처를 구성 요소별로 이해하기
```
[Client VPC]                                    [Service VPC]
  Client EC2 (Public, :80)                        Service EC2 (Private, :8080)
        │                                                ▲
        │ SERVICE_URL = VPC Lattice Generated Domain     │
        ▼                                                │
  ============ VPC Lattice Service Network ============
        │                                                │
   [Service Network] ← VPC Association (Client VPC)
        │
   [Service: skills-lattice-order-service] ← Service Association (→ Service Network)
        │
   [Listener: HTTP/80] → Forward
        │
   [Target Group: HTTP/8080, Instance Type] → Health Check /health
        │
   [Target: Service EC2]
```

- **Service Network**: "어떤 서비스들을, 어떤 VPC들이 쓸 수 있는가"를 정의하는 상위 개념입니다. Client VPC를 여기에 **Association**시키면, 그 VPC 안의 리소스들이 Lattice로 노출된 서비스를 호출할 수 있게 됩니다.
- **Service**: 실제로 호출 가능한 하나의 논리적 엔드포인트(도메인)입니다. Lattice가 자동으로 도메인을 생성해주고(Generated Domain), Client 앱은 이 도메인으로 요청을 보냅니다 — IP 주소를 몰라도 서비스 이름 기반으로 통신할 수 있다는 점이 핵심 편의성입니다.
- **Listener/Target Group**: ALB와 개념이 똑같습니다. Listener가 요청을 받아 Target Group으로 Forward하고, Target Group이 실제 Service EC2(인스턴스)를 Health Check하며 트래픽을 보냅니다.
- **VPC Association의 Security Group**: Client VPC CIDR(10.61.0.0/16)에서 TCP/80만 허용 — "이 Service Network를 쓸 수 있는 진짜 출처가 어디인지"를 한 번 더 좁히는 계층입니다.

### Security Group 설계에서 가장 중요한 개념 — Managed Prefix List
- Service EC2의 SG는 `0.0.0.0/0`을 허용하면 안 되고, **VPC Lattice Managed Prefix List** 소스만 허용해야 합니다.
- 이건 AWS가 관리하는 "VPC Lattice가 사용하는 IP 대역 목록"을 자동으로 알려주는 기능입니다. Service EC2 입장에서 보면 실제 요청이 Client EC2가 아니라 **VPC Lattice의 내부 프록시**에서 오는 것처럼 보이기 때문에, "Lattice를 거쳐온 트래픽만 믿고 받겠다"는 걸 이 Prefix List로 표현하는 겁니다. `0.0.0.0/0`을 허용하면 "누구든 직접 접근 가능"해져서 문제의 "VPC를 안 거치고 우회 접근 방지" 취지가 깨집니다.

### 애플리케이션 응답에 `via=vpc-lattice`가 왜 들어가야 하는가
- 이건 채점/검증 목적입니다 — 응답에 이 필드가 있다는 건 "Client가 실제로 자기 코드로 직접 DB/서비스를 호출한 게 아니라, **VPC Lattice 경유로 정상적으로 라우팅됐다**"는 걸 증명하는 마커입니다.

**한 줄 요약**: "VPC를 직접 잇지 않고, Service Network라는 논리적 레이어로 서비스 디스커버리와 트래픽 라우팅을 대신 처리하는" 애플리케이션 레벨 서비스 메시 패턴입니다.

## 모듈 3. Cloud Event Handling — "이번엔 SG 하나만 정확히, 그림까지 그대로"

### v8의 Cloud Event Handling과 무엇이 다른가
- v8에서는 SG/IAM/EC2종료/EC2타입변경 4개 Rule을 다 만들었지만, 이번엔 **"SG Inbound 규칙 추가" 단 하나**에 집중합니다. 대신 훨씬 더 구체적인 스펙(정확한 API 이벤트명, 정확한 아키텍처 다이어그램)이 주어졌습니다 — 실전에서는 이렇게 "범위는 좁지만 정밀도를 요구하는" 형태로도 자주 나옵니다.

### 다이어그램을 그대로 코드로 옮기는 연습
문제에 주어진 다이어그램을 흐름으로 풀면:
```
[누군가 Security Group에 Inbound 규칙 추가] (AuthorizeSecurityGroupIngress API 호출)
        │
   [CloudTrail] → API Event 기록 (skills-ceh-cloudtrail)
        │
   [EventBridge Rule] → skills-ceh-sg-change-rule (default event bus에서 이 이벤트 패턴 감지)
        │ Invoke
   [Lambda: skills-ceh-remediate-fn]
        ├─ Revoke ingress → Security Group을 다시 Inbound 0개로 복구
        ├─ Publish → SNS Topic(skills-ceh-alert-topic)에 알림 발행
        └─ Logs → CloudWatch Logs(/aws/lambda/skills-ceh-remediate-fn)에 기록
```

### 이 모듈에서 특히 중요한 디테일들
- **환경변수로 대상을 하드코딩하지 않고 주입**: `PROTECTED_SECURITY_GROUP_ID`, `SNS_TOPIC_ARN`을 Lambda 환경변수로 넘긴다는 건, Lambda 코드 자체는 "어떤 SG를, 어떤 Topic으로" 몰라도 되게 만드는 설계입니다 — 코드와 설정의 분리(모듈2의 CDN Function에서 봤던 KVS와 같은 철학)가 여기서도 반복됩니다.
- **Event Pattern이 "EC2 AuthorizeSecurityGroupIngress"로 매우 구체적**: EventBridge Rule의 이벤트 패턴을 이 정확한 API 액션명으로 좁혀야, 다른 API 호출에는 반응하지 않고 정확히 이 이벤트에만 트리거됩니다.
- **최종 제출 시점에 Inbound 규칙 0개여야 한다**는 조건과 **"skills-ceh-protected-sg에 22번 포트를 임시로 열어서 검증 가능하되 180초 내 제거"**라는 유의사항이 연결되어 있습니다. 즉 채점 위원이 실제로 규칙을 추가해서 "자동 복구가 180초 내에 작동하는지"를 실시간으로 검증한다는 뜻입니다 — 그래서 Lambda가 **빠르고 확실하게** 반응해야 하고 (EventBridge→Lambda 체인의 지연시간을 고려해도 충분히 여유), IAM 권한(RevokeSecurityGroupIngress 등)이 정확히 부여돼 있어야 합니다.

**한 줄 요약**: v8의 4-Rule 버전을 "SG 하나"로 압축하고, 실시간 자동복구 시간(180초)까지 채점하는 더 정밀한 버전입니다. 원리는 동일하니 v8 설명을 그대로 적용하면 됩니다.

## 모듈 4. Event-driven Pod Scaling with AWS SQS — "vf의 EKS Scaling + Fargate 믹스"

### vf의 EKS Scaling 모듈과 무엇이 같고 다른가
- 같은 점: SQS → KEDA(Pod 스케일링) → Karpenter(Node 스케일링) 3단 체인은 완전히 동일한 패턴입니다.
- 다른 점: 이번엔 **KEDA/Karpenter 컨트롤러 자체를 EC2 NodeGroup이 아니라 Fargate에서 돌립니다.** "관제탑(컨트롤러)은 서버리스로, 실제 작업자(Worker Pod)만 EC2로"라는 구성이 새로운 포인트입니다.

### 왜 컨트롤러를 Fargate에 놓는가 (vf에서는 별도 NodeGroup + taint였는데)
- vf에서는 "Addon NodeGroup에 taint를 걸어서 App과 분리"하는 방식을 썼습니다.
- 이번엔 아예 **Fargate**(서버리스 컴퓨팅, 노드 관리 자체가 필요 없음)에 KEDA/Karpenter를 올려버립니다. Fargate Profile로 `keda`, `karpenter` Namespace를 지정하면, 그 네임스페이스의 Pod는 자동으로 Fargate 위에 뜹니다.
- **장점**: EC2 노드를 하나 고정으로 띄워둘 필요가 없어서 관리 부담이 더 줄어듭니다. **결국 목적은 vf와 동일 — "스케일링 시스템 자체는 App의 부하와 무관하게 안정적으로 떠 있어야 한다"**는 것이며, 이번엔 그 방법을 taint 대신 Fargate 분리로 구현한 겁니다.
- Worker Pod(sqs-worker)는 Fargate가 아니라 **Karpenter가 만든 EC2 Worker Node**에서 돌아야 합니다 — 이건 Fargate가 아직 세밀한 커스텀 요구(특정 인스턴스 타입, GPU 등) 대응이 제한적이라, "가변적이고 커스터마이징이 필요한 워크로드는 Karpenter+EC2"로 두는 실무 패턴을 반영합니다.

### IRSA(IAM Roles for Service Accounts) — 왜 각 컴포넌트마다 필요한가
- `keda-operator`, `karpenter`, `sqs-worker-sa` 각각에 IRSA(ServiceAccount에 `eks.amazonaws.com/role-arn` annotation을 걸어 AWS IAM Role과 매핑)가 필요한 이유:
  - KEDA는 SQS 큐 길이를 **조회(GetQueueAttributes 등)**할 권한이 필요합니다.
  - Karpenter는 **EC2 인스턴스를 생성/삭제**할 권한이 필요합니다.
  - Worker Pod는 SQS 메시지를 **수신/삭제**할 권한이 필요합니다.
- 세 역할이 하는 일이 완전히 다르므로 각자 별도의 최소 권한 Role을 갖는 것 — Pod 레벨에서 세밀하게 권한을 나누는 IRSA의 핵심 가치입니다 (Node의 IAM Role을 공유하면 모든 Pod가 같은 권한을 갖게 되어 과다권한 문제가 생김).

### NodeSelector 이중 조건이 의미하는 것
```yaml
nodeSelector:
  karpenter.sh/nodepool: skills-sqs-nodepool
  skills-nodepool: event-worker
```
- 첫 번째는 "Karpenter가 관리하는 노드 중 이 NodePool에서 만든 노드"라는 시스템 라벨.
- 두 번째는 NodePool 스펙에 정의한 커스텀 라벨(`skills-nodepool=event-worker`) — 문제에서 요구한 대로 NodePool 자체에 라벨을 심어두고, Pod가 그 라벨을 지정해서 매칭시키는 구조입니다. 이렇게 이중으로 매칭 조건을 거는 이유는, Karpenter가 여러 NodePool을 운영할 때 "정확히 이 노드풀에서 만든 노드에만" Worker Pod가 배치되도록 확실히 못 박기 위함입니다.

### KEDA 트리거 스펙 읽는 법
- `queueLength: 2` → Pod 1개당 큐 메시지 2건을 목표로 스케일 계산 (메시지 10건이면 Pod 5개 필요하다고 계산)
- `min 0, max 6`: 메시지가 없으면 아예 0개까지 줄어듭니다 — vf 모듈(최소 1개 유지)과 다른 정책입니다. "완전한 이벤트 기반(메시지 없으면 워커도 없음)"을 지향하는 설계라는 차이를 눈여겨보세요.
- `pollingInterval 15초 이하`: KEDA가 몇 초마다 큐 길이를 확인하는지, `cooldownPeriod 30초 이하`: 스케일 인 전에 얼마나 기다리는지 — 너무 빨리 스케일 인하면 방금 들어온 메시지를 처리할 Pod가 곧바로 사라지는 "떨림(flapping)" 현상이 생기니 이를 완화하는 값입니다.

### Consolidation Policy — Karpenter의 비용 최적화 기능
- `spec.disruption.consolidationPolicy`는 "활용도가 낮은 노드를 자동으로 통합/제거"하는 정책입니다. vf에서 "60초 후 반환"이라는 조건과 개념적으로 동일 — Karpenter가 계속 노드를 최소한으로 유지하도록 만드는 설정입니다.

**한 줄 요약**: vf의 "SQS→KEDA→Karpenter" 3단 체인은 그대로이되, 이번엔 컨트롤러들을 Fargate라는 서버리스 레이어에 올려서 "관제 시스템 자체의 인프라 관리 부담"까지 없애는 더 발전된 버전입니다.

## 세 개 과제지를 관통하는 최종 정리

지금까지 본 세 개의 과제지(vf, v8, hwp)는 매번 다른 서비스 조합을 쓰지만, 결국 같은 원칙의 변주라는 걸 알 수 있습니다.

1. **DB 선택은 "쿼리 패턴의 복잡도"가 기준**: 단순 Key-Value/이벤트 처리엔 DynamoDB, 복잡한 인덱스/쿼리가 필요하면 DocumentDB.
2. **네트워크 격리 + 최소 노출**: DB/내부 서비스는 항상 Private, 외부 접근은 ALB/Lattice/CloudFront 같은 게이트웨이 하나로만 — 이 원칙은 세 과제 전부에서 반복됩니다.
3. **설정과 코드의 분리**: KVS(CDN), 환경변수(Lambda), Secrets Manager(DocumentDB) — 전부 "코드는 그대로 두고 설정값만 바꿔서 동작을 바꾼다"는 동일한 철학입니다.
4. **이벤트 기반 자동화 체인**: CloudTrail→EventBridge→Lambda, SQS→KEDA→Karpenter, S3→Step Functions — "무언가 발생하면 자동으로 다음 단계가 실행"되는 패턴이 매번 등장합니다.
5. **컨트롤러/시스템 구성요소와 실제 워크로드의 물리적 분리**: taint(vf) 또는 Fargate(hwp)로 "스케일링 인프라 자체"를 안정적으로 유지하는 게 목적입니다.
6. **최소 권한을 컴포넌트 단위(Role/IRSA)로 촘촘히 분리**: 어느 모듈이든 예외 없이 등장하는 요구사항입니다.

결국 이 6가지 프레임을 체화하면, 서비스 이름이 매번 바뀌어도 "이 요구사항이 왜 있는가"를 스스로 유추하며 문제를 풀 수 있게 됩니다.
