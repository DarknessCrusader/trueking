# 모듈 1. DocumentDB based NoSQL Application

## skills-nosql-docdb-cluster / skills-nosql-docdb-instance-1
- **Cluster/Instance 분리 아키텍처**: DocumentDB(그리고 Aurora)는 "스토리지 계층(Cluster)"과 "컴퓨트 계층(Instance)"을 분리한 구조입니다. Cluster는 여러 AZ에 걸쳐 복제되는 공유 스토리지를 관리하고, Instance는 그 스토리지에 붙어 쿼리를 처리하는 컴퓨트 노드입니다. 이 분리 덕분에 Instance를 추가/제거해도(Read Replica 확장 등) 스토리지 복제는 영향받지 않습니다.
- **db.t3.medium**: Instance의 컴퓨트 크기를 결정하는 값으로, 이 문서의 쿼리 처리량과 메모리 용량을 좌우합니다.
- **Storage Encryption + alias/skills-nosql-docdb (KMS)**: 디스크에 저장되는 모든 데이터(스토리지, 스냅샷, 로그)를 이 KMS 키로 암호화합니다. 이 설정은 Cluster 생성 시점에만 지정 가능하고 이후 변경이 불가능하다는 게 이론적으로 중요한 제약입니다.
- **TLS Enabled**: 클라이언트-서버 간 네트워크 전송 구간의 암호화를 강제합니다. DocumentDB는 기본적으로 TLS를 요구하므로, 클라이언트가 신뢰할 CA 인증서 체인 없이 연결하면 핸드셰이크 자체가 실패합니다.
- **Backup Retention 1일 이상**: 자동 백업(스냅샷)을 보관하는 최소 기간으로, 장애/실수 발생 시 특정 시점으로 복구(Point-in-Time Restore)할 수 있는 범위를 결정합니다.
- **외부 직접 노출 금지**: DocumentDB는 애초에 VPC 내부 전용 서비스(퍼블릭 엔드포인트 자체를 지원하지 않음)이므로, 이 조건은 "Private Subnet에 배치하고, 접근 가능한 Security Group 소스를 Client EC2로만 한정"하라는 뜻으로 해석해야 합니다.

## skills-nosql-client-ec2 (EC2, Client Application)
- 이 EC2는 사용자의 외부 요청(TCP 8080)을 받아, 내부적으로 DocumentDB에 쿼리를 날리는 애플리케이션 계층입니다. Public IP를 가지므로 외부에서 직접 접근 가능하지만, DocumentDB 자체는 여전히 이 EC2를 거쳐야만 도달 가능합니다 — "DB는 숨기고 애플리케이션만 노출"하는 표준 계층화입니다.
- **docdb_client.py를 수정하지 않고 배포**한다는 조건은, 코드 로직 자체는 고정 불변이고 **환경(설정, 인프라)만 올바르게 맞춰서 그 코드가 정상 동작하게 만드는 게 채점의 핵심**이라는 걸 시사합니다.

## skills-nosql-docdb-secret (Secrets Manager)
- Secret에 담긴 `username`, `password`, `host` 세 값은 애플리케이션이 부팅 시점에 API로 조회해서 DB 연결 문자열을 조립하는 데 쓰입니다.
- **host에 Scheme/Port를 포함하지 않는다는 제약의 이론적 의미**: Secret은 "순수한 자격증명 데이터"만 담당하고, 프로토콜(mongodb://)이나 포트(27017) 같은 "연결 방식에 대한 지식"은 애플리케이션 코드가 소유하도록 책임을 분리한 설계입니다. 이렇게 하면 나중에 포트나 접속 방식이 바뀌어도 Secret 자체는 건드릴 필요가 없습니다.
- EC2에 부여된 IAM Role은 이 특정 Secret ARN에 대한 GetSecretValue 권한만 가져야 최소 권한 원칙을 지킵니다.
- Secrets Manager를 쓰는 근본적인 이유는 **자격증명을 코드나 환경변수에 평문으로 하드코딩하지 않기 위함**이며, Secrets Manager는 이 값들을 자체적으로 암호화 저장하고, 접근 시마다 감사 로그(CloudTrail)를 남깁니다.

## skills_retail 데이터베이스 및 컬렉션(orders/products/sessions)
- **왜 DynamoDB가 아니라 DocumentDB(MongoDB 호환)인가**: DynamoDB는 키 설계(PK/SK)에 따라 조회 패턴이 제한되고, 새로운 조회 패턴이 필요할 때마다 GSI를 추가해야 합니다. 반면 MongoDB 호환 문서형 DB는 **복합 인덱스, 범위 쿼리, TTL 인덱스** 등을 훨씬 유연하게 조합할 수 있어, 이 과제처럼 여러 컬렉션에 걸쳐 다양한 인덱스 조건이 요구되는 상황에 적합합니다.
- **orders 컬렉션의 인덱스**:
  - `{orderId: 1} unique`: 주문 ID의 유일성을 DB 레벨에서 강제 — 애플리케이션 로직에서 중복 체크를 하지 않아도, DB가 중복 삽입을 거부합니다.
  - `{customerId: 1, createdAt: -1}`: "이 고객의 주문을 최신순으로" 조회하는 패턴을 위한 복합 인덱스. 인덱스의 필드 순서가 중요한데, `customerId`로 먼저 좁히고 그 안에서 `createdAt` 내림차순 정렬이 인덱스에 이미 반영되어 있어 매우 빠른 조회가 가능합니다.
  - `{status: 1, dueAt: 1}`: "특정 상태(예: 미배송)이면서 마감일이 임박한 주문"을 찾는 운영 쿼리를 위한 인덱스.
- **products 컬렉션**: `{productId: 1} unique`(상품 ID 유일성), `{warehouseId: 1, stock: 1}`(특정 창고의 재고 현황 조회용).
- **sessions 컬렉션의 TTL 인덱스**: `{expiresAt: 1} TTL expireAfterSeconds: 0`는 MongoDB의 자동 문서 삭제 기능으로, `expiresAt` 필드에 저장된 시각이 지나면 백그라운드 프로세스가 그 문서를 자동으로 삭제합니다. `expireAfterSeconds: 0`은 "그 시각 자체가 만료 시점"이라는 의미입니다. 이 기능은 **BSON Date 타입** 필드에만 정상 동작하므로, 데이터 적재 시 문자열이 아닌 실제 날짜 객체로 저장해야 합니다. 세션처럼 유효기간이 있는 임시 데이터를 자동 청소하는 데 이상적입니다.
  - `{customerId: 1, lastSeen: -1}`: 고객별 최근 세션을 조회하는 패턴.

# 모듈 2. Simplify Service Networking with VPC Lattice

## skills-lattice-client-vpc / skills-lattice-service-vpc
- 서로 다른 VPC에 Client와 Service를 분리 배치하는 이유는, 실무에서 마이크로서비스가 여러 팀·여러 계정·여러 VPC에 걸쳐 운영되는 상황을 재현하기 위함입니다. 이 두 VPC 사이에는 **VPC Peering이나 Transit Gateway 같은 네트워크 레벨의 직접 연결을 만들지 않는다**는 게 이 모듈의 핵심 제약입니다.

## VPC Lattice의 이론적 위치
- 기존 VPC 간 통신 방법(Peering, Transit Gateway)은 **네트워크(3-4계층, IP 라우팅)** 수준에서 두 VPC를 하나의 네트워크처럼 잇는 방식입니다. 이 방식은 VPC가 늘어날수록 연결 관리가 기하급수적으로 복잡해지고(N개 VPC를 다 이으려면 최대 N(N-1)/2개의 Peering), CIDR 충돌 문제도 생깁니다.
- **VPC Lattice**는 이 문제를 애플리케이션 계층(7계층)에서 해결합니다: VPC 간 네트워크를 직접 잇지 않고, "이 서비스를 이 VPC들에서 쓸 수 있게 하겠다"는 **서비스 단위의 논리적 연결**만 선언합니다. 실제 트래픽은 AWS가 관리하는 Lattice의 데이터 플레인을 통해 전달되며, 사용자는 라우팅 테이블이나 CIDR을 신경 쓸 필요가 없습니다.

## skills-lattice-sn (Service Network)
- Service Network는 "어떤 VPC들이, 어떤 Service들에 접근할 수 있는가"를 정의하는 상위 컨테이너입니다. Client VPC를 이 Service Network에 **연결(Association)**시키면, 그 VPC 안의 리소스(Client EC2)가 이 네트워크에 속한 Service를 호출할 수 있는 권한을 얻습니다.
- **Association Security Group**: VPC를 Service Network에 연결할 때, "이 VPC의 어느 CIDR에서 오는 트래픽만 허용할지"를 한 번 더 제한하는 계층입니다. Client VPC CIDR(10.61.0.0/16)만 허용하면, 설령 나중에 다른 VPC가 실수로 잘못 연결되더라도 이 SG가 2차 방어선이 됩니다.

## skills-lattice-order-service (Service)
- Service는 실제로 호출 가능한 논리적 엔드포인트로, 생성 시 AWS가 자동으로 고유한 도메인(Generated Domain)을 부여합니다. Client 애플리케이션은 이 도메인을 향해 요청을 보내면 되고, 실제 트래픽이 어느 VPC의 어느 인스턴스로 가는지는 Lattice가 알아서 라우팅합니다 — 이게 서비스 디스커버리를 코드에서 몰라도 되게 해주는 핵심 편의성입니다.
- 이 Service를 Service Network(skills-lattice-sn)에 **연결(Service Association)**해야, 그 Service Network에 속한 VPC들이 비로소 이 Service를 호출할 수 있게 됩니다(Service를 만드는 것과 Service Network에 연결하는 것은 별개의 단계입니다).

## skills-lattice-order-tg (Target Group)
- ALB의 Target Group과 개념이 완전히 동일합니다: 실제 요청을 처리할 백엔드(Service EC2)의 목록을 관리하고, Health Check(HTTP `/health`)로 정상 상태인 대상에만 트래픽을 보냅니다.
- Type을 Instance로 지정하면 EC2 인스턴스 ID 기준으로 대상을 등록합니다(Lambda나 IP 기반 Target Group도 가능하지만 이 과제는 Instance 타입).

## skills-lattice-http-listener (Listener)
- Service에 붙는 진입점으로, 특정 포트(HTTP/80)로 들어온 요청을 어느 Target Group으로 전달할지 결정하는 규칙입니다. Default Action이 Target Group으로의 Forward라는 건, 별도 경로 기반 분기 없이 모든 요청을 하나의 Target Group으로 보낸다는 뜻입니다.

## Service EC2 Security Group — VPC Lattice Managed Prefix List
- **Managed Prefix List의 이론**: AWS가 관리하며 지속적으로 갱신되는 "특정 서비스가 사용하는 IP 대역 목록"입니다. VPC Lattice 전용 Prefix List를 SG의 허용 소스로 지정하면, "Lattice의 데이터 플레인에서 오는 트래픽만" 정확히 허용하고 그 외의 모든 직접 접근(0.0.0.0/0을 포함해서)은 차단됩니다.
- 이게 중요한 이유는, Client가 Service EC2에 접근할 때 실제로는 **Client의 IP가 아니라 Lattice 프록시의 IP에서** 요청이 온 것처럼 보이기 때문입니다. 만약 SG를 0.0.0.0/0으로 열어두면 "VPC를 안 거치고 직접 붙어도 되는" 우회 경로가 생겨버려, VPC Lattice를 도입한 근본 취지(모든 트래픽을 Lattice 경유로 강제)가 깨집니다.

## Client/Service Application의 via/service 필드
- 응답에 `service.via=vpc-lattice` 같은 마커를 포함시키는 건, 애플리케이션이 우연히 같은 응답을 내는 게 아니라 **실제로 VPC Lattice 경로를 거쳐서 통신했다는 걸 증명**하기 위한 채점/검증용 필드입니다.

# 모듈 3. Cloud Event Handling

이 모듈은 v8 과제의 Cloud Event Handling과 이론적으로 완전히 동일한 패턴(CloudTrail→EventBridge→Lambda→SNS)이며, 감시 대상을 "SG Inbound 추가" 하나로 좁힌 버전입니다.

## skills-ceh-vpc / skills-ceh-ec2 / skills-ceh-protected-sg
- `skills-ceh-protected-sg`는 이 모듈의 "보호 대상" 그 자체입니다. **최종 제출 시점에 Inbound 규칙이 0개여야 한다**는 조건은, 이 SG가 "평상시엔 아무 인바운드도 허용하지 않는 완전 폐쇄 상태가 정상"이라는 걸 의미하며, 누군가(또는 채점 스크립트)가 여기에 규칙을 추가하면 그게 곧 "위반 이벤트"가 됩니다.

## skills-ceh-alert-topic (SNS Topic)
- Standard 타입 SNS는 순서 보장이 없는 대신 처리량 제약이 적어, "위반이 발생했다"는 단발성 알림 메시지를 발행하는 용도로 충분합니다.

## skills-ceh-remediate-fn (Lambda)
- **PROTECTED_SECURITY_GROUP_ID / SNS_TOPIC_ARN을 환경변수로 주입**하는 이론적 의미: 이 Lambda 코드 자체는 "어떤 SG를, 어떤 Topic으로" 다뤄야 하는지 하드코딩하지 않고, 실행 환경에서 값을 주입받습니다. 이렇게 하면 코드는 그대로 두고, 다른 SG/Topic에도 동일 Lambda 코드를 재사용할 수 있습니다 — CDN 모듈의 KeyValueStore, Workflow 모듈의 환경변수와 같은 "설정과 로직 분리" 원칙의 반복입니다.
- 이 Lambda가 수행하는 세 가지 동작(Inbound 규칙 복구, SNS 알림 발행, CloudWatch Logs 기록)은 각각 "자동 복구", "인간에게 알림", "감사 추적 남기기"라는 서로 다른 목적을 가진 사이드 이펙트들입니다.

## skills-ceh-sg-change-rule (EventBridge Rule)
- 이 Rule의 이벤트 패턴은 `AuthorizeSecurityGroupIngress`라는 **정확한 API 액션 이름**에 매칭됩니다. 이 정밀도가 중요한 이유는, EC2 관련 API 호출은 수십 가지가 있는데 그중 정확히 "인바운드 규칙 추가"에 해당하는 액션에만 반응해야, 관련 없는 다른 API 호출(예: 인스턴스 조회)에 불필요하게 Lambda가 실행되는 걸 막을 수 있기 때문입니다.

## skills-ceh-cloudtrail (CloudTrail Trail, Logging Enabled)
- CloudTrail이 켜져 있어야 API 호출 자체가 기록되고, 그 기록이 EventBridge로 전달됩니다. Trail이 비활성 상태면 EventBridge Rule이 아무리 잘 정의되어도 애초에 감지할 이벤트 자체가 발생하지 않습니다.

## 180초 이내 자동 복구 요구의 이론적 함의
- 이 조건은 "이벤트가 발생한 순간부터, CloudTrail 기록 → EventBridge 필터링 → Lambda 호출 → SG 복구까지의 전체 파이프라인 지연시간이 충분히 짧아야 한다"는 걸 실전에서 검증하는 조건입니다. 각 단계(CloudTrail의 기록 지연, EventBridge의 처리 지연, Lambda의 콜드 스타트 등)가 이론적으로 수 초~수십 초 내에 끝나야 이 SLA를 만족할 수 있습니다.

# 모듈 4. Event-driven Pod Scaling with AWS SQS

## skills-sqs-cluster (EKS) + Fargate Profile 2종
- **skills-sqs-fp-keda / skills-sqs-fp-karpenter**: Fargate Profile은 "특정 네임스페이스의 Pod는 EC2 노드가 아니라 AWS가 완전관리하는 서버리스 컴퓨트(Fargate)에서 실행하라"는 매핑입니다. `keda` 네임스페이스와 `karpenter` 네임스페이스를 각각 지정하면, KEDA Operator와 Karpenter Controller Pod가 Fargate 위에서 뜹니다.
- **왜 컨트롤러를 Fargate에 두는가**: 이 두 컨트롤러는 "스케일링 시스템 자체를 운영하는 인프라"이므로, 이들이 Worker Pod의 스케일 인/아웃에 영향을 받아 같이 흔들리면 안 됩니다. Fargate는 애초에 "고정된 EC2 노드"라는 개념 자체가 없어, Worker Pod들이 배치되는 EC2 NodePool과 완전히 물리적으로 분리된 실행 환경을 제공합니다 — taint를 걸어 EC2 NodeGroup을 분리하던 이전 방식보다 한 단계 더 격리도가 높은 접근입니다.

## skills-sqs-queue (SQS)
- KEDA가 이 큐의 메시지 수를 지표로 삼아 Worker Pod 수를 결정합니다. Visibility Timeout(30초 이상)은 "한 Consumer가 메시지를 받아 처리 중일 때, 다른 Consumer에게 그 메시지가 다시 보이지 않게 숨기는 시간"으로, Worker의 처리 소요시간(PROCESSING_SECONDS)보다 충분히 길어야 같은 메시지가 중복 처리되는 걸 막을 수 있습니다.

## keda/keda-operator, karpenter/karpenter, skills-sqs/sqs-worker-sa (IRSA)
- 세 ServiceAccount 각각에 `eks.amazonaws.com/role-arn` annotation을 걸어 IAM Role과 매핑하는 **IRSA(IAM Roles for Service Accounts)** 메커니즘입니다.
  - KEDA Operator Role: SQS 큐 속성 조회(GetQueueAttributes) 권한만.
  - Karpenter Role: EC2 인스턴스 생성/삭제, 관련 태그/라벨 조작 권한.
  - sqs-worker-sa Role: SQS 메시지 수신(ReceiveMessage)·삭제(DeleteMessage) 권한만.
- 이렇게 Pod 단위로 권한을 세분화하는 이유는, 만약 Node의 IAM Role을 모든 Pod가 공유한다면 그 노드 위의 모든 Pod가 동일한(때로는 과도한) 권한을 갖게 되기 때문입니다. IRSA는 "같은 노드 위에 있어도 Pod마다 정확히 필요한 권한만" 갖도록 세밀하게 분리합니다.

## worker.py (Worker Application)
- SQS를 폴링해서 메시지를 받아 `PROCESSING_SECONDS`만큼 처리를 시뮬레이션하고 메시지를 삭제하는 Consumer 로직입니다. `SQS_QUEUE_URL`, `AWS_REGION` 환경변수를 코드에 하드코딩하지 않고 외부에서 주입받는 것 역시 지금까지 계속 반복된 "설정과 코드 분리" 원칙입니다.

## sqs-worker (Deployment, skills-sqs 네임스페이스)
- **Node Selector 이중 조건**(`karpenter.sh/nodepool=skills-sqs-nodepool` + `skills-nodepool=event-worker`)의 이론: 앞의 라벨은 Karpenter가 노드를 만들 때 시스템적으로 자동 부여하는 라벨이고, 뒤의 라벨은 NodePool 스펙에 사용자가 직접 정의한 커스텀 라벨입니다. 두 조건을 동시에 요구함으로써, "이 NodePool이 만든 노드에만" Worker Pod가 정확히 배치되도록 이중으로 못박습니다. 클러스터에 여러 NodePool이 공존할 가능성을 고려한 안전장치입니다.
- **Fargate가 아닌 Karpenter EC2에서 실행되어야 하는 이유**: Fargate는 아직 특정 인스턴스 타입 지정, GPU, 커스텀 AMI 같은 세밀한 요구를 완전히 지원하지 못하는 제약이 있어, "가변적이고 인프라 커스터마이징이 필요할 수 있는 워크로드"는 Karpenter+EC2 조합을 쓰는 게 실무에서도 일반적입니다.

## sqs-worker-scaledobject / sqs-worker-trigger-auth (KEDA)
- **queueLength: 2**: Pod 1개당 메시지 2건을 처리 목표로 잡는다는 뜻으로, KEDA는 대략 `필요 Pod 수 = ceil(큐의 메시지 수 / 2)`로 목표 Replica를 계산합니다.
- **min 0 / max 6**: 메시지가 아예 없으면 Pod를 0개까지 줄이는 정책입니다(vf 과제의 EKS Scaling 모듈에서 min 1이었던 것과 대비되는 설계 — "완전한 이벤트 기반"을 지향해, 아무 이벤트가 없을 때는 컴퓨트 자원을 전혀 쓰지 않겠다는 철학입니다).
- **pollingInterval 15초 이하 / cooldownPeriod 30초 이하**: 폴링 주기가 너무 길면 반응이 느리고, cooldown이 너무 짧으면 메시지가 막 들어온 직후 Pod가 급격히 줄어드는 "떨림(flapping)" 현상이 생깁니다. 이 두 값의 균형이 안정적인 오토스케일링의 핵심입니다.
- **TriggerAuthentication**: KEDA가 SQS API를 호출할 때 어떤 인증 수단을 쓸지 정의하는 리소스로, Pod Identity(IRSA와 유사한 최신 방식)를 참조하도록 구성합니다.

## skills-sqs-nodepool / skills-sqs-nodeclass (Karpenter)
- **NodePool Label `skills-nodepool=event-worker`**: 이 NodePool이 만드는 모든 노드에 자동으로 부여되는 라벨로, Worker Pod의 nodeSelector가 이 값을 정확히 지정해 매칭시킵니다.
- **spec.disruption.consolidationPolicy**: 유휴하거나 활용도가 낮은 노드를 Karpenter가 자동으로 통합·제거하는 정책입니다. 이 값이 있어야, 부하가 줄어든 뒤 남는 여분의 EC2 노드가 자동으로 정리되어 "과제 종료 시 Pod 1개/Node 1대"라는 최종 상태로 수렴할 수 있습니다.
- Allowed Instance Types(t3.small, t3.medium)는 Karpenter가 Pending Pod의 요구 자원에 맞춰 이 목록 안에서 가장 적합한 크기를 골라 프로비저닝하는 데 쓰이는 제약 조건입니다.

| Pod 단위 세분화된 IAM 권한 | 같은 노드 위에서도 Pod마다 다른 권한 부여 | IRSA |
| 이벤트 기반 완전 축소(Scale-to-Zero) | 이벤트가 없을 때 컴퓨트 자원을 0으로 줄임 | KEDA min=0 |
| 노드 자동 통합/회수 | 저활용 노드를 자동으로 정리해 비용 최소화 | Karpenter Consolidation |
