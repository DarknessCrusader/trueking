# 클라우드컴퓨팅 제2과제 (Workflow / Analytics / Event / MSK) — 개념 이해 가이드

이번 과제지는 지난번(NoSQL/CDN/EKS/Logging)과 완전히 다른 4개 주제입니다. 리전도 전부 다릅니다.

| 모듈 | 리전 | 핵심 주제 |
|---|---|---|
| 1. Workflow | ap-southeast-1 | 서버리스 오케스트레이션 (Step Functions) |
| 2. Read-time data analytics | ap-northeast-2 | 실시간 스트림 분석 (Kinesis + Flink) |
| 3. Cloud Event Handling | eu-west-1 | 보안 이벤트 감지·자동복구 (EventBridge + CloudTrail) |
| 4. MSK | ap-northeast-1 | Kafka 기반 이벤트 스트리밍 |

각 모듈이 "왜 이런 구조를 요구하는지" 중심으로 정리했습니다.

---

## 모듈 1. Workflow — "여러 서비스를 순서대로 엮어서 하나의 처리 흐름을 만든다"

### 이 모듈이 테스트하려는 것
Lambda 하나로 모든 걸 처리하지 않고, **S3 → Lambda → DynamoDB**로 이어지는 각 단계를 **Step Functions**가 오케스트레이션하도록 분리하는 능력입니다. "왜 굳이 Step Functions를 쓰는가?"가 핵심 질문입니다.

### 왜 Lambda 하나로 안 하고 Step Functions인가
- Lambda 하나에 모든 로직(파일 검증→계산→저장→에러처리)을 다 넣으면: 실패 시 어디서 실패했는지 추적이 어렵고, 재시도/분기 로직이 코드 안에 뒤섞입니다.
- Step Functions는 **State Machine**으로 각 단계를 시각적으로 분리합니다: "읽기 단계 실패 시 → error 폴더로", "성공 시 → 변환 단계로" 같은 분기/에러 핸들링을 **인프라 레벨(JSON 정의)**에서 관리합니다.
- **Standard 타입**을 쓰는 이유: Standard는 실행 이력이 90일간 보존되고 정확히 한 번(Exactly-once) 실행을 보장 — 성적 데이터처럼 "중복 처리되면 안 되는" 배치성 워크플로우에 적합합니다. (반대로 Express는 대량/짧은 실행에 적합하며 at-least-once)

### S3 폴더 구조가 왜 3개로 나뉘어 있는가 (input / processed / error)
- 이건 "상태를 폴더 위치로 표현"하는 매우 흔한 데이터 파이프라인 패턴입니다.
- `/input/` = 아직 처리 안 된 원본, `/processed/` = 정상 처리 완료, `/error/` = 검증 실패 또는 워크플로우 오류
- 이렇게 하면 "지금 파일이 어느 상태인지"를 별도 DB 조회 없이 **S3 경로만 보고 알 수 있습니다.** 재처리도 쉬워집니다 (error 폴더의 파일만 다시 돌리면 됨).
- S3 업로드 이벤트(PutObject)가 Step Functions 실행을 트리거하는 구조 → **EventBridge(또는 S3 Event Notification)**로 "파일이 /input/에 올라오면 State Machine 실행" 연결이 필요합니다.

### DynamoDB 키 설계 (PK: studentId, SK: examDate)
- 한 학생이 여러 번 시험을 볼 수 있으므로, "학생+시험일자" 조합이 유일한 레코드가 됩니다.
- PK만으로는 "이 학생의 모든 시험 기록"을 정렬된 형태로 조회할 수 있고, SK(examDate)로 범위 조회(특정 기간 성적)도 가능해집니다 — Composite Key의 전형적인 활용입니다.

### IAM Role이 2개로 나뉜 이유
- `wsc2026-lambda-student-role`: Lambda가 S3 읽기 + DynamoDB 쓰기 권한만 필요
- `wsc2026-stepfunction-student-role`: Step Functions가 Lambda를 **호출(invoke)**할 권한만 필요
- 각자 "자기가 하는 일에 필요한 권한만" 갖도록 분리 — 최소 권한 원칙이 역할 단위로도 적용됩니다.

**한 줄 요약**: "각 단계를 독립된 컴포넌트로 쪼개고, Step Functions가 그 사이의 흐름/에러 처리를 오케스트레이션한다"는 서버리스 워크플로우의 기본 패턴입니다.

## 모듈 2. Read-time Data Analytics — "데이터가 쌓이자마자 즉시 분석하려면?"

### 이 모듈이 테스트하려는 것
배치(하루 한 번 분석)가 아니라 **스트림이 들어오는 즉시 분석**하는 아키텍처, 그리고 그 스트림 인프라를 안전한 네트워크(Private Subnet) 안에 구성하는 능력입니다.

### 네트워크 구조부터 이해하기
```
[Internet]
    │
[ALB] ← Public Subnet (analytics-pub-a/b)
    │
[EC2 (주문 로그 생성 앱)] ← Private Subnet (analytics-priv-a/b)
    │  (아웃바운드는 NAT Gateway를 통해 나감)
    ▼
[Kinesis Data Stream]
    │
[Managed Apache Flink]
```
- EC2가 Private Subnet에 있는 이유: 외부에서 EC2로 직접 접근하면 안 되고, **ALB를 거쳐야만** 접근 가능해야 하기 때문 (문제에 명시됨). Private Subnet + ALB(Public Subnet)는 "웹 서버를 외부에 직접 노출하지 않는" 표준 3-tier 패턴입니다.
- **AZ를 a/b 두 개로 나눈 이유**: "고가용성" 요구사항 때문. 한 AZ가 장애 나도 다른 AZ가 살아있게 하려는 목적 — Public/Private 서브넷 각각 2개씩(AZ당 1개)이 기본 패턴입니다.
- **SSM 접속**: Private Subnet의 EC2는 SSH로 직접 접속할 방법이 마땅치 않습니다(퍼블릭 IP가 없으므로). SSM(Session Manager)은 **EC2에 IAM Role만 붙어있으면 인터넷/베스천 없이도** AWS 콘솔/CLI로 접속 가능하게 해주는 서비스 — Private 리소스 관리의 표준 방법입니다. (단, SSM 엔드포인트 통신을 위해 NAT Gateway나 VPC Endpoint가 필요합니다)

### Kinesis Data Stream — "실시간 데이터의 파이프"
- 로그가 발생하는 즉시 Kinesis로 보내면, 여러 소비자(Consumer)가 동시에 같은 데이터를 읽을 수 있습니다(SQS와 달리 메시지가 소비돼도 안 사라지고 보존기간 동안 남아있음 — 여러 명이 같은 스트림을 볼 수 있는 게 핵심 차이).
- **On-demand 모드**: 트래픽 예측이 어려울 때 처리량(샤드 수)을 AWS가 자동 조절 — Provisioned 모드처럼 미리 샤드 수를 정할 필요가 없습니다.

### Managed Apache Flink — "SQL로 스트림을 실시간 쿼리"
- Flink는 스트리밍 데이터 처리 엔진인데, 이 과제는 "Flink 애플리케이션 프로그래밍은 금지, SQL만 사용"이라고 명시했습니다 — 즉 Studio Notebook에서 **Kinesis Stream을 테이블처럼 취급**해서 SQL을 날리는 것이 핵심입니다.
- 예시 쿼리 두 개를 보면 스트리밍 SQL의 특징이 보입니다:
  - `WHERE event_time > CURRENT_TIMESTAMP - INTERVAL '1' MINUTE` → **슬라이딩 윈도우 없이도** "최근 1분"이라는 시간 조건을 걸어 계속 흐르는 데이터에 대해 지속적으로 결과를 갱신하는 쿼리입니다.
  - `GROUP BY product_name` → 스트림에서도 배치처럼 집계가 가능한데, 결과가 **계속 업데이트되는 뷰**라는 점이 배치 SQL과 다릅니다.
- 이게 되려면 Flink가 Kinesis Stream을 소스로 인식하도록 **테이블 매핑(연결)**을 먼저 정의해야 합니다.

**한 줄 요약**: "Private Subnet + ALB로 보호된 앱 → Kinesis로 스트림 수집 → Flink SQL로 그 자리에서 바로 분석"하는, 배치 없이 실시간으로 인사이트를 뽑는 구조입니다.

## 모듈 3. Cloud Event Handling — "누군가 몰래 보안 설정을 바꾸면 자동으로 되돌리고 알린다"

### 이 모듈이 테스트하려는 것
AWS 리소스에 대한 **API 호출 자체를 감시**해서, 위험한 변경이 감지되면 **자동으로 대응(복구+알림)**하는 이벤트 기반 보안 자동화입니다. 이건 클라우드 보안 운영(CloudOps/SecOps)의 핵심 패턴입니다.

### 전체 흐름을 먼저 그려보면
```
[누군가 EC2 보안그룹에 인바운드 규칙 추가] 같은 API 호출
        │
[CloudTrail] → 모든 API 호출(Management Events)을 기록
        │
[EventBridge Rule] → CloudTrail 이벤트 중 "위험한 패턴"만 필터링해서 감지
        │
[Lambda] → 감지되면 실행: 원래 상태로 복구 (예: 규칙 삭제) + SNS로 알림
        │
[SNS Topic] → 관리자에게 메시지 발송 (이메일/문자 구독 가능)
```

### 왜 CloudTrail이 먼저 필요한가
- EventBridge는 기본적으로 "리소스 상태 변화(예: EC2 상태 변경)"는 일부 자동으로 감지하지만, **"누가 어떤 API를 호출했는가"(예: AuthorizeSecurityGroupIngress 같은 API 이름 단위)**를 감지하려면 CloudTrail이 그 API 호출을 로그로 남기고, EventBridge가 그 CloudTrail 이벤트를 규칙으로 받아야 합니다.
- **Management Events(Read/Write)**를 켜야 하는 이유: 보안그룹 변경, IAM Role 변경 같은 건 전부 "관리 이벤트"이지 "데이터 이벤트"(S3 객체 읽기/쓰기 같은)가 아니기 때문입니다.

### 4개 EventBridge Rule이 감지하는 것 = "권한/가용성에 영향을 주는 변경들"
| Rule | 왜 위험한가 |
|---|---|
| SG 인바운드 규칙 추가 | 외부에서 접근 가능한 포트가 늘어남 → 공격 표면 확대 |
| IAM Role 변경 | 권한이 은밀하게 상승(privilege escalation)할 수 있음 |
| EC2 종료 | 서비스 가용성에 직접 영향 (실수든 악의든) |
| EC2 인스턴스 타입 변경 | 비용 급증 가능성 (예: t3.micro → 초대형 인스턴스) — "비용 상 위협"이 여기 해당 |

- 즉 이 4개는 "보안(SG, IAM)"과 "비용/가용성(종료, 타입변경)" 두 축을 대표하는 이벤트들입니다. 문제 서두의 "보안 또는 비용상 위협"이라는 문구가 그대로 매핑됩니다.

### Lambda의 역할 — 탐지가 아니라 "대응"
- EventBridge Rule은 "감지"만 하고, 실제 원복/알림 로직은 Lambda가 담당합니다.
- 예: SG 인바운드 규칙이 추가된 걸 감지하면 → Lambda가 `RevokeSecurityGroupIngress`로 그 규칙을 다시 제거(자동 복구) → 동시에 SNS로 "누가 몇 시에 무엇을 변경했다"는 알림 발행.
- Lambda Role의 최소 권한: 복구에 필요한 최소한의 EC2/IAM 관련 write 권한 + SNS Publish 권한만.

**한 줄 요약**: "모든 API 호출 기록(CloudTrail) → 위험 패턴 필터링(EventBridge) → 자동 복구 + 알림(Lambda+SNS)"이라는 이벤트 기반 보안 자동화(SOAR: Security Orchestration, Automation and Response)의 축소판입니다.

## 모듈 4. MSK — "Kafka를 관리형으로, IAM 인증으로 안전하게"

### 이 모듈이 테스트하려는 것
Kinesis와는 다른 스트리밍 플랫폼인 **Kafka(MSK)**의 구조, 그리고 IAM 기반 인증으로 접근을 제어하는 방법입니다.

### 왜 Kinesis 말고 MSK(Kafka)를 또 쓰는가 — 개념적 차이 이해하기
- Kinesis는 AWS 완전관리형(샤드 개념)이라 운영 부담이 적지만, Kafka 생태계(커넥터, 다양한 클라이언트 라이브러리, Exactly-once semantics 등)를 그대로 쓰고 싶을 땐 MSK를 선택합니다.
- 이 과제에서 MSK는 "IAM 인증 전용"으로 구성하라고 명시 — 일반 Kafka는 SASL/SCRAM이나 인증서 기반 인증을 쓰지만, **MSK는 IAM 정책만으로 Kafka 접근을 통제**할 수 있는 AWS 확장 기능을 제공합니다. 이 경우 "누가 이 Topic에 Produce/Consume 할 수 있는가"가 전부 IAM Policy 문서로 관리됩니다.

### 네트워크 구조 (모듈 2와 유사한 패턴)
```
msk-vpc (192.168.0.0/16)
 ├─ Public Subnet (msk-pub-a/d) → IGW 연결
 └─ Private Subnet (msk-priv-a/d) → NAT 연결
        │
   [MSK Broker들] → Private Subnet에 배치 (외부에 노출되면 안 됨)
   [wsc2026-sensor-producer EC2] → Private Subnet에서 MSK로 메시지 발행
```
- MSK 브로커를 **Private**에 두는 이유: 센서 데이터를 다루는 스트리밍 인프라를 인터넷에 직접 노출하면 안 되기 때문 — Kafka 자체엔 기본적으로 세밀한 네트워크 방화벽 개념이 약해서, VPC 격리가 1차 방어선이 됩니다.
- **고가용성**: 브로커를 여러 AZ(pub-a/pub-d 같은 서로 다른 AZ)에 걸쳐 배치해서 한 AZ 장애에도 클러스터가 살아있게 합니다.

### Topic 설계 — Partition과 Replication Factor의 의미
| Topic | Partition | Replication Factor | 의미 |
|---|---|---|---|
| wsc2026-sensor-raw | 3 | 2 | 원본 센서 데이터, 병렬 처리를 위해 3개로 분산 |
| wsc2026-sensor-alert | 1 | 2 | 이상치 알림, 순서가 중요하므로 파티션 1개(전체 순서 보장) |

- **Partition 수**: 병렬 처리량을 결정합니다. Partition이 많을수록 여러 Consumer가 동시에 나눠 처리할 수 있지만, 순서 보장은 파티션 내에서만 됩니다. sensor-raw는 파티션이 3개라 "센서별 순서"만 보장되고(같은 sensorId는 같은 파티션으로), 전체 순서는 보장 안 됨.
- **Replication Factor 2**: 브로커 장애에 대비해 각 파티션 데이터를 2개 브로커에 복제 — 고가용성을 위한 필수 설정.
- **PK: sensorId**로 파티셔닝한다는 건, Kafka Producer가 메시지를 보낼 때 `sensorId`를 파티션 키로 사용해서 **같은 센서의 데이터는 항상 같은 파티션**에 가도록(=순서 보장) 만든다는 뜻입니다.

### 전체 파이프라인
```
[wsc2026-sensor-producer EC2] → wsc2026-sensor-raw Topic에 Produce
        │
[wsc2026-sensor-consumer Lambda] (Trigger: MSK - sensor-raw)
   → 원본 데이터 처리 → DynamoDB(wsc2026-sensor-data) 저장
   → 이상치 감지 시 wsc2026-sensor-alert Topic에 Produce (추정)
        │
[wsc2026-sensor-alert-consumer Lambda] (Trigger: MSK - sensor-alert)
   → 알림 처리, 필요 시 S3(wsc2026-sensor-alert-bucket)에 오류/알림 데이터 저장
```
- **Lambda의 MSK Trigger**: Lambda가 폴링 방식으로 MSK 브로커에서 메시지를 가져와 실행됩니다 (Kafka Consumer 역할을 Lambda가 대신 수행) — 별도 EC2로 Consumer 앱을 상시 띄울 필요가 없는 서버리스 소비 패턴입니다.
- Lambda가 MSK에 접근하려면 IAM 인증 클러스터이므로, Lambda 실행 Role에 **Kafka 관련 IAM 액션(kafka-cluster:Connect, ReadData 등)**을 최소 권한으로 부여해야 합니다.

**한 줄 요약**: "Private VPC에 격리된 MSK(IAM 인증) → EC2가 Produce → Lambda가 서버리스로 Consume → 결과를 DynamoDB/S3에 적재"하는, Kafka 생태계를 서버리스와 결합한 이벤트 스트리밍 구조입니다.

## 4개 모듈을 관통하는 공통 사고방식

지난 과제(NoSQL/CDN/EKS/Logging)와 마찬가지로, 이번에도 몇 가지 반복되는 설계 원칙이 있습니다.

1. **관측 가능한 상태를 물리적 위치/구조로 표현**: S3 input/processed/error 폴더, DynamoDB 복합키 — "데이터가 지금 어떤 상태인지"를 별도 조회 없이 구조 자체로 알 수 있게 설계.
2. **이벤트 기반 트리거 체인**: S3 업로드→Step Functions, API 호출→CloudTrail→EventBridge→Lambda, MSK 메시지→Lambda Trigger — 전부 "무언가 발생하면 자동으로 다음 단계가 실행"되는 구조.
3. **네트워크 격리(Public/Private 분리)**: 모듈 2, 4 둘 다 "처리 서버는 Private, 외부 노출은 ALB/IGW를 통해서만"이라는 동일한 패턴을 반복 — 실무에서 가장 기본이 되는 네트워크 보안 설계.
4. **서버리스 우선(Lambda 중심 소비)**: 별도 상시 서버 없이 Lambda가 이벤트/스트림을 소비하도록 구성 — 운영 부담과 비용을 줄이는 선택.
5. **최소 권한을 역할 단위로 촘촘히 분리**: Lambda Role, Step Functions Role, EC2 Role이 전부 따로 존재 — "누가 무엇을 할 수 있는가"를 컴포넌트별로 명확히 나눔.

이번 과제도 세부 이름/포트는 암기가 필요하지만, "이 요구사항이 왜 존재하는가"는 이 5가지 프레임에 대입해보면 대부분 설명이 됩니다.
