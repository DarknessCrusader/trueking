## 🔄 모듈 1. Workflow

### `wsc2026-student-score-bucket-<비번호>` (S3)
> **핵심**: 폴더 위치 = 상태 머신. 별도 상태 DB 없이 경로만으로 처리 상태를 표현

| 프리픽스 | 상태 |
|---|---|
| `/input/` | 처리 대기 |
| `/processed/` | 처리 완료 |
| `/error/` | 처리 실패 |

- 채점 시 processed/error 비어있어야 함 → 리소스 역할과 별개로 "테스트 흔적 제거" 조건

### `wsc2026-student-score` (DynamoDB)
> **핵심**: PK `studentId` + SK `examDate` = "학생+시험일" 복합키 (한 학생이 여러 번 시험 봄)

- SK 범위 쿼리로 "이 학생의 모든 시험 기록"을 examDate 순 정렬 조회 가능

### `wsc2026-student-score-workflow` (Step Functions)
> **핵심**: 여러 단계의 순서·재시도·분기를 선언적으로 관리 (Lambda 코드 안에 뒤섞지 않음)

- **왜 오케스트레이션이 필요한가**: 단계별 실패 지점 추적 어려움 + 재시도/분기 로직이 코드 안에 뒤엉킴 → State Machine이 이를 시각적·선언적으로 분리
- **Standard 타입**: 실행 이력 90일 보존 + Exactly-once 보장 (Express는 대량/짧은 실행 + At-least-once)
  - 성적 데이터 = 중복 처리되면 안 되는 워크로드 → Standard 적합
- **트리거 연결**: S3 자체엔 "업로드 시 Step Functions 실행" 개념이 없음 → EventBridge가 중간에서 Object Created 이벤트를 받아 StartExecution 호출

### IAM Role 2종
> **핵심**: 역할이 다르면 권한도 반드시 다르게 분리

| Role | 담당 | 필요 권한 |
|---|---|---|
| `wsc2026-lambda-student-role` | Lambda | S3 읽기, DynamoDB 쓰기 |
| `wsc2026-stepfunction-student-role` | Step Functions | Lambda 호출, S3 파일 이동 |

## 📈 모듈 2. Read-time Data Analytics

### `analytics-vpc` (10.20.0.0/16)
> **핵심**: Public(관문) + Private(실제 처리) 분리, AZ별 라우팅 테이블 분리로 장애 격리

- `analytics-priv-a-rtb` / `analytics-priv-b-rtb`로 AZ별 분리 → 한 AZ의 NAT 장애가 다른 AZ까지 전파 안 됨

### `wsc2026-analytics-ec2` (Private Subnet)
> **핵심**: 외부에서 직접 도달 불가, ALB를 통해서만 접근

- **SSM 접근**: SSH 키/베스천 없이 IAM Role만으로 Session Manager 접속 가능 → 이 통신도 NAT나 VPC Endpoint(Interface)를 거쳐야 성사

### `wsc2026-analytics-alb` / `wsc2026-analytics-tg`
> **핵심**: 역방향 프록시 — Public에서 받아 Private EC2로 전달

### `wsc2026-order-stream` (Kinesis)
> **핵심**: 여러 소비자가 동일 스트림을 각자 독립적으로 읽을 수 있는 발행-구독형 (SQS와 근본적으로 다름)

- **On-demand Capacity Mode**: 샤드 수를 AWS가 트래픽에 맞춰 자동 조절 (Provisioned는 사람이 직접 관리)

### `wsc2026-analytics-flink` (Managed Apache Flink)
> **핵심**: 스트림 = 무한히 흐르는 테이블. SQL로 지속 쿼리(Continuous Query) 실행

- "애플리케이션 프로그래밍 금지, SQL만" → 저수준 DataStream API 대신 선언적 Flink SQL만 사용

**쿼리 1: 최근 1분간 주문 수**
```
시간 조건을 계속 재평가하며 결과를 지속 갱신
→ 배치 SQL의 "한 번 실행하고 끝"과 근본적으로 다름
→ 이벤트 시간(Event Time) 매핑이 선행되어야 정확히 동작
```

**쿼리 2: 상품별 누적 매출**
```
GROUP BY가 새 이벤트마다 해당 그룹의 집계값을 갱신
→ 지속적으로 최신 상태를 반영하는 살아있는 뷰
```

### IAM Role 2종
| Role | 방향 | 권한 |
|---|---|---|
| `wsc2026-alaytics-ec2-role` | 생산자 | Kinesis PutRecord |
| `wsc2026-analytics-flink-role` | 소비자 | Kinesis GetRecords 등 |

## 🛡️ 모듈 3. Cloud Event Handling

### `event-vpc` (172.16.0.0/16)
> **핵심**: Public만 2개(감시 대상 EC2도 Public에 있어도 무방) — 목적이 "네트워크 격리"가 아니라 "설정 변경 감지"이므로

### `wsc2026-event-ec2` / `wsc2026-event-sg`
> **핵심**: 이 SG 자체가 "보호 대상" — 최소한으로 시작해야 변화를 명확히 감지

### EventBridge Rule 4종
> **핵심**: 보안(공격 표면) + 비용/가용성(중단·과다지출), 두 축의 위협을 대표

| Rule | 감지 대상 | 위협 종류 |
|---|---|---|
| `wsc2026-sg-change-rule` | SG 인바운드 추가 | 보안 — 공격 표면 확대 |
| `wsc2026-role-change-rule` | IAM Role 변경 | 보안 — 권한 은밀 상승 |
| `wsc2026-ec2-terminate-rule` | EC2 종료 | 가용성 — 서비스 중단 |
| `wsc2026-ec2-type-change-rule` | 인스턴스 타입 변경 | 비용 — 예상치 못한 지출 |

- 각 Rule의 이벤트 패턴은 **정확한 API 액션 이름**에만 매칭 → 관련 없는 API 호출엔 반응 안 함

### `wsc2026-event-trail` (CloudTrail)
> **핵심**: Management Events(Read/Write) — 리소스 생성/수정/삭제/조회의 관리 목적 API 호출 기록

- Data Events(S3 객체 읽기/쓰기 등)와는 별개 카테고리
- Trail이 꺼져있으면 EventBridge Rule이 아무리 잘 정의돼도 애초에 감지할 이벤트가 없음

### Lambda (정책 위반 감지 시 실행)
> **핵심**: 탐지(EventBridge)와 대응(Lambda)의 역할 분리

- 이렇게 나누는 이유: 새 위협 유형 추가 시 Rule만 추가하면 됨 (Lambda 전체를 안 바꿔도 됨)

### `wsc2026-event-alert` (SNS)
> **핵심**: 발행자(Lambda)와 구독자(관리자)가 완전히 분리된 구조

## 📡 모듈 4. MSK

### `msk-vpc` (192.168.0.0/16)
> **핵심**: 브로커/Producer를 Private에 배치 → 인터넷 직접 접근 경로 차단 (Analytics 모듈과 동일 원리)

### `wsc2026-msk-cluster` (IAM 인증)
> **핵심**: Kafka 프로토콜 위에 IAM 자격증명을 실어, ACL 관리 없이 IAM Policy로 통합 관리

- 일반 Kafka는 SASL/SCRAM·mTLS가 표준 → MSK는 IAM 인증이라는 AWS 확장 기능 제공
- Private + Multi-AZ 배치 → AZ 장애에도 클러스터 생존
- `kafka.t3.small` = 브로커 하나의 컴퓨트 크기

### Topic 2종
> **핵심**: Partition = 병렬성, Replication Factor = 내결함성

| Topic | Partition | RF | 이유 |
|---|---|---|---|
| `wsc2026-sensor-raw` | 3 | 2 | 대량 센서 데이터 병렬 처리 |
| `wsc2026-sensor-alert` | 1 | 2 | 알림은 전체 순서 보장 필요 |

- **PK `sensorId`로 파티셔닝**: 같은 센서 메시지는 항상 같은 파티션 → 그 센서의 순서는 보장 (파티션 간 순서는 보장 안 됨)
- **RF 2**: 각 파티션을 2개 브로커에 복제 → 한 브로커 장애에도 데이터 유지

### `wsc2026-sensor-producer` (EC2)
> **핵심**: Private이어도 MSK와 같은 VPC 내부 통신이라 인터넷 경유 불필요

### Lambda 2종 (MSK Trigger)
> **핵심**: 이벤트 소스 매핑이 Lambda를 상시 Consumer처럼 동작하게 만듦 (별도 EC2 상시 프로세스 불필요)

| 함수 | 트리거 Topic |
|---|---|
| `wsc2026-sensor-consumer` | `wsc2026-sensor-raw` |
| `wsc2026-sensor-alert-consumer` | `wsc2026-sensor-alert` |

- Lambda가 Private Subnet의 MSK에 접근하려면 Lambda 자체도 그 VPC에 연결(ENI)돼야 함

### `wsc2026-sensor-data` (DynamoDB)
> **핵심**: PK `sensorId` + SK `timestamp` — "엔티티+시간" 복합키 패턴 재등장

### `wsc2026-sensor-alert-bucket-<비번호>` (S3)
> **핵심**: 오류 데이터/알림 이력 아카이브

### IAM Role 2종
| Role | 방향 | 권한 |
|---|---|---|
| `wsc2026-msk-ec2-role` | 생산자 | MSK Produce |
| `wsc2026-msk-lambda-role` | 소비자 | MSK Consume + DynamoDB 쓰기 |

- IAM 인증 클러스터라 일반 IAM Action이 아닌 `kafka-cluster:*` 전용 액션 사용

## 🎯 핵심 이론 요약

| 이론 개념 | 정의 | 적용 사례 |
|---|---|---|
| 워크플로우 오케스트레이션 | 여러 단계의 순서·재시도·분기를 선언적으로 관리 | Step Functions |
| 상태를 물리적 위치로 표현 | 별도 DB 없이 경로 자체로 상태를 드러냄 | S3 input/processed/error |
| 발행-구독 스트림 | 여러 소비자가 동일 데이터를 독립적·반복적으로 읽음 | Kinesis |
| 지속 쿼리 (Continuous Query) | 결과가 계속 갱신되는 스트리밍 SQL | Flink |
| 감사 로그 기반 이벤트 탐지 | 모든 API 호출 기록 + 위험 패턴만 필터링 | CloudTrail + EventBridge |
| 탐지-대응 분리 | 감지와 실제 조치를 다른 컴포넌트로 분리 | Event Handling |
| IAM 통합 인증 (Kafka) | 별도 ACL 없이 IAM Policy로 스트리밍 접근 통제 | MSK |
| 파티션·복제 | 병렬성 + 내결함성 동시 확보 | Kafka Topic |
| 서버리스 스트림 소비 | 상시 프로세스 없이 이벤트 시에만 함수 실행 | Lambda MSK Trigger |
