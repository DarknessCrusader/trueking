# 모듈 1. Workflow

## wsc2026-student-score-bucket-<비번호> (S3 버킷)
- **/input, /processed, /error 세 프리픽스**: S3에는 실제 "폴더"가 존재하지 않고, 객체 키(Key) 문자열에 `/`가 포함된 것을 UI가 폴더처럼 보여줄 뿐입니다. 하지만 이 프리픽스 구조는 논리적으로 **파이프라인의 상태 머신을 파일 위치로 표현**하는 역할을 합니다: input=처리 대기, processed=처리 완료, error=처리 실패. 이 구조 덕분에 별도의 상태 DB 없이도 "지금 파일이 어떤 상태인지"가 경로만으로 드러납니다.
- **채점 시 processed/error가 비어있어야 한다**는 조건은 리소스의 역할과는 별개로, "테스트 흔적을 지우고 처음 상태로 제출하라"는 채점 준비 조건입니다.

## wsc2026-student-score (DynamoDB 테이블)
- PK `studentId` + SK `examDate`: 한 학생이 여러 번 시험을 본다는 도메인 특성상, 학생 하나만으로는 레코드를 유일하게 식별할 수 없고 "학생+시험일자" 조합이 필요합니다. 이 복합키 구조 덕분에 "이 학생의 모든 시험 기록"을 examDate 순으로 정렬 조회하는 것도 자연스럽게 가능해집니다(SK 범위 쿼리).
- 채점 시 모든 데이터를 삭제해야 한다는 조건 역시, 리소스 자체의 역할이 아니라 "재현 가능한 초기 상태로 채점받기 위한" 절차적 요구입니다.

## wsc2026-student-score-workflow (Step Functions State Machine)
- **오케스트레이션의 이론적 필요성**: 하나의 처리 과정을 (1) S3 파일 읽기 (2) 성적 계산 및 등급 산출 (3) DynamoDB 저장이라는 여러 독립 단계로 나눌 때, 이 단계들의 실행 순서·오류 시 분기·재시도 정책을 Lambda 코드 내부의 if/else와 try/except로 처리하면 "무엇이 어디서 실패했는지"를 추적하기 어렵고, 로직이 점점 뒤엉킵니다. State Machine은 이 흐름 자체를 **선언적으로(각 단계를 State로)** 표현해, 실행 이력이 시각적으로 남고 각 단계의 성공/실패가 명확히 구분됩니다.
- **Standard 타입의 이론적 특성**: 실행 이력을 최대 90일 보존하며, 각 실행이 정확히 한 번(Exactly-once)만 처리되도록 보장합니다. 반대로 Express 타입은 대량의 짧은 실행에 최적화되어 있고 최소 한 번(At-least-once) 보장만 합니다. 성적 데이터처럼 "중복 계산·중복 저장이 발생하면 안 되는" 워크로드는 Standard가 이론적으로 더 적합합니다.
- **S3 업로드를 트리거로 잇는 메커니즘**: S3 자체에는 "파일이 올라오면 Step Functions를 실행하라"는 개념이 내장되어 있지 않으므로, 중간에 이벤트 전달 계층(예: EventBridge)이 필요합니다. S3의 Object Created 이벤트가 EventBridge를 거쳐 Step Functions StartExecution API를 호출하는 구조로 연결됩니다.

## wsc2026-lambda-student-role / wsc2026-stepfunction-student-role (IAM Role)
- 두 Role은 각각 **Lambda가 실제로 무엇을 하는가**(S3 읽기, DynamoDB 쓰기)와 **Step Functions가 실제로 무엇을 하는가**(Lambda 호출, S3 파일 이동)라는, 서로 완전히 다른 책임을 반영합니다. 최소 권한 원칙은 "역할이 다르면 권한도 반드시 다르게 나뉘어야 한다"는 이론을 실제 리소스 단위로 구현한 것입니다.

# 모듈 2. Read-time Data Analytics

## analytics-vpc (10.20.0.0/16) 및 서브넷 구조
- Public 2개(a/b) + Private 2개(a/b) 구조는 **"외부에서 접근 가능한 관문"과 "내부에서만 도달 가능한 실제 처리 자원"을 분리**하는 3-Tier 네트워크의 표준 형태입니다. AZ를 a/b 두 곳으로 나눈 이유는 "한 AZ가 통째로 장애 나도 서비스가 살아있어야 한다"는 고가용성 요구 때문입니다.
- **analytics-priv-a-rtb / analytics-priv-b-rtb로 라우팅 테이블을 AZ별로 분리**: 만약 Private 서브넷들이 하나의 공용 라우팅 테이블(따라서 하나의 NAT)만 쓴다면, 그 NAT가 있는 AZ가 죽었을 때 다른 AZ의 Private 자원까지 인터넷이 끊깁니다. AZ별로 라우팅 테이블과 NAT를 분리하는 건 이 장애 전파(Blast Radius)를 그 AZ 안으로 가두기 위함입니다.

## wsc2026-analytics-ec2 (EC2, Private Subnet)
- Private Subnet에 배치되어 외부에서 직접 도달할 방법이 없고, **ALB를 통해서만** 트래픽을 받습니다. 이는 애플리케이션 서버를 인터넷에 직접 노출하지 않는 표준 보안 패턴입니다.
- **SSM 접근**: Private Subnet의 EC2는 SSH 키/베스천 호스트 없이도, EC2에 부여된 IAM Role만으로 AWS Systems Manager Session Manager가 브라우저/CLI 기반의 셸 접속을 제공합니다. 이 통신 자체가 AWS 서비스와의 통신이므로, NAT Gateway를 통하거나 SSM 관련 VPC Endpoint(Interface Endpoint)를 둬야 실제로 연결이 성사됩니다.

## wsc2026-analytics-alb / wsc2026-analytics-tg (ALB/Target Group)
- ALB는 Public Subnet에 위치하며, 사용자의 HTTP 요청을 받아 Private Subnet의 EC2(Target Group에 등록된)로 전달하는 **역방향 프록시** 역할을 합니다. 이 구조 덕분에 EC2 자체는 퍼블릭 IP나 인터넷 게이트웨이 라우팅이 전혀 필요 없습니다.

## wsc2026-order-stream (Kinesis Data Stream)
- Kinesis는 **여러 소비자가 동일한 스트림을 각자 독립적으로 읽을 수 있는** 발행-구독형 스트리밍 저장소입니다(SQS처럼 한 번 소비되면 사라지는 큐와 근본적으로 다른 성질). 데이터는 지정된 보존 기간 동안 스트림에 남아있으므로, "지금 만든 소비자 애플리케이션"도 그 이전에 들어온 데이터를 처음부터 다시 읽을 수 있습니다.
- **On-demand Capacity Mode**: Kinesis는 내부적으로 데이터를 여러 샤드(병렬 처리 단위)로 분산하는데, Provisioned 모드는 이 샤드 수를 사람이 직접 관리해야 하지만 On-demand는 AWS가 트래픽에 따라 자동으로 샤드 수를 조절합니다. 트래픽 패턴을 예측하기 어려운 실시간 주문 로그에 적합한 선택입니다.

## wsc2026-analytics-flink (Managed Apache Flink Studio Notebook)
- Flink는 스트림을 **연속적으로 흐르는 무한 테이블**처럼 취급해 SQL로 질의할 수 있게 해주는 스트림 처리 엔진입니다. "애플리케이션 프로그래밍 금지, SQL만 허용"이라는 조건은, Flink의 저수준 DataStream API(Java/Scala/Python 코드로 직접 스트림 로직을 짜는 방식) 대신, **Flink SQL이라는 선언적 인터페이스**만 쓰라는 제약입니다.
- **"최근 1분간 총 주문 수" 쿼리의 이론**: 스트림 SQL에서 시간 조건(`event_time > CURRENT_TIMESTAMP - INTERVAL '1' MINUTE`)을 걸면, 시스템은 이 조건을 계속 재평가하며 결과를 지속적으로 갱신합니다. 배치 SQL의 "한 번 실행하고 끝"과 달리, 스트리밍 SQL의 결과는 **끊임없이 최신 상태를 반영하는 살아있는 뷰**라는 게 근본적 차이입니다. 이걸 정확히 동작시키려면 Flink가 스트림의 어느 필드를 "이벤트 시간(Event Time)"으로 볼지 지정하는 시간 속성 매핑이 선행되어야 합니다.
- **"상품별 누적 매출" 쿼리의 이론**: `GROUP BY`가 배치처럼 한 번의 결과를 내는 게 아니라, 새 이벤트가 들어올 때마다 해당 그룹의 집계값을 갱신하는 **지속 쿼리(Continuous Query)**로 동작합니다.

## wsc2026-alaytics-ec2-role / wsc2026-analytics-flink-role
- EC2는 Kinesis에 데이터를 쓰는(PutRecord) 최소 권한, Flink는 Kinesis에서 데이터를 읽는(GetRecords 등) 최소 권한만 가져야 합니다. 생산자와 소비자의 권한이 명확히 분리된 형태입니다.

# 모듈 3. Cloud Event Handling

## event-vpc (172.16.0.0/16)
- 이 모듈은 EC2 하나만 감시 대상이므로, Private Subnet 없이 Public 서브넷만 두 개(pub-a/pub-b) 구성됩니다. 감시 대상 EC2가 Public에 있어도 상관없는 건, 이 모듈의 목적이 "네트워크 격리"가 아니라 "설정 변경 감지·복구"이기 때문입니다.

## wsc2026-event-ec2 / wsc2026-event-sg
- 이 EC2와 SG는 "보호 대상"입니다. SG의 인바운드 규칙이 부적절하게 추가되는 상황을 감지하는 게 이 모듈의 핵심 시나리오이므로, SG는 최소한(예: 필요한 최소 포트만)으로 시작해야 그 변화를 명확히 감지·복구할 수 있습니다.

## wsc2026-sg-change-rule / wsc2026-role-change-rule / wsc2026-ec2-terminate-rule / wsc2026-ec2-type-change-rule (EventBridge Rules)
- 이 4개 규칙은 "보안(공격 표면 확대)"과 "가용성/비용(서비스 중단, 예상치 못한 지출)"이라는 두 축의 위협을 대표합니다:
  - SG 인바운드 추가: 의도치 않게 열린 포트로 외부 공격 표면이 넓어짐
  - IAM Role 변경: 권한이 은밀하게 상승할 수 있는(Privilege Escalation) 경로
  - EC2 종료: 서비스 중단으로 직결되는 가용성 위협
  - EC2 인스턴스 타입 변경: 값비싼 인스턴스로 몰래 변경되는 비용 위협
- 각 Rule의 **이벤트 패턴(Event Pattern)**은 CloudTrail이 기록한 API 호출 이벤트 중 "이 특정 API 액션 이름"에 정확히 매칭되는 것만 필터링합니다. 이 패턴 매칭은 EventBridge 내부에서 이벤트가 도착하는 즉시 평가되므로, 별도의 폴링 없이 실시간에 가깝게 반응합니다.

## CloudTrail (wsc2026-event-trail)
- CloudTrail은 계정 내 모든 API 호출을 기록하는 감사 로그 서비스입니다. **Management Events(Read/Write)**는 리소스를 생성·수정·삭제하거나 조회하는 "관리 목적의 API 호출"(EC2 인스턴스 시작, SG 규칙 변경 등)을 가리키며, S3 객체 읽기/쓰기 같은 "데이터 목적의 API 호출(Data Events)"과는 별개 카테고리입니다. 이 모듈이 감지하려는 이벤트는 전부 Management Events에 속하므로 이 옵션이 켜져 있어야 합니다.
- CloudTrail이 기록한 이벤트는 자동으로 EventBridge의 기본 이벤트 버스로 전달되어(관리 이벤트의 경우), Rule이 이를 필터링할 수 있는 소스가 됩니다.

## Lambda 함수(정책 위반 감지 시 실행)
- 이 Lambda는 "탐지"가 아니라 **대응(복구+알림)**을 담당합니다. EventBridge Rule이 감지와 라우팅을 맡고, Lambda가 실제 조치(예: 추가된 SG 규칙을 다시 제거)를 실행하고, 그 결과를 SNS로 알리는 구조입니다. 탐지와 대응을 분리하는 이유는, 하나의 Lambda가 모든 걸 다 하면 새로운 위협 유형이 추가될 때마다 그 Lambda 코드 전체를 바꿔야 하지만, 이렇게 나누면 Rule만 추가/변경하면 되는 유연성이 생깁니다.

## wsc2026-event-alert (SNS Topic)
- SNS는 발행-구독 모델의 알림 서비스로, Lambda가 이 Topic에 메시지를 Publish하면, 관리자가 미리 구독해둔 채널(이메일, SMS 등)로 자동 전달됩니다. Lambda 코드는 "누가 구독하고 있는지" 전혀 몰라도 되고, 그저 Topic ARN에 메시지를 보내기만 하면 됩니다 — 발행자와 구독자가 완전히 분리된 구조입니다.

# 모듈 4. MSK

## msk-vpc (192.168.0.0/16) 및 서브넷 구조
- Public(msk-pub-a/d) + Private(msk-priv-a/d) 4개 서브넷 구조는 앞선 Analytics 모듈과 동일한 원리입니다. 브로커와 Producer EC2를 Private에 두어 인터넷의 직접 접근 경로를 차단합니다.

## wsc2026-msk-cluster (MSK 클러스터, IAM 인증)
- Kafka 자체는 원래 SASL/SCRAM이나 mTLS 인증서 기반 인증을 표준으로 쓰지만, **MSK IAM 인증**은 AWS가 Kafka 프로토콜 위에 IAM 자격증명을 실을 수 있게 확장한 기능입니다. 이 방식을 쓰면 "누가 어떤 Topic에 Produce/Consume 가능한가"를 전부 **IAM Policy 문서로 통합 관리**할 수 있어, 별도의 Kafka ACL 관리 체계를 따로 둘 필요가 없어집니다.
- **Private 배치와 고가용성**: 브로커를 여러 AZ의 Private 서브넷(pub-a, pub-d처럼 서로 다른 AZ)에 걸쳐 배치해, 한 AZ 장애가 나도 클러스터 전체가 살아있게 합니다.
- `kafka.t3.small` 인스턴스 클래스는 브로커 하나가 실행되는 컴퓨트 자원의 크기를 결정합니다.

## wsc2026-sensor-raw / wsc2026-sensor-alert (Kafka Topic)
- **Partition의 이론**: 하나의 Topic은 여러 Partition으로 나뉘고, 각 Partition은 독립적으로 여러 Consumer가 병렬로 처리할 수 있는 단위입니다. `wsc2026-sensor-raw`가 Partition 3개인 이유는 "여러 센서로부터 오는 대량 데이터를 병렬 처리"하기 위함이고, `wsc2026-sensor-alert`가 Partition 1개인 이유는 "알림은 전체 순서가 중요하므로" 단일 파티션으로 전체 순서를 보장하기 위함입니다.
- **Replication Factor 2**: 각 파티션 데이터를 2개의 브로커에 복제해 저장하는 것으로, 한 브로커가 장애 나도 다른 복제본에서 데이터를 잃지 않고 계속 서비스할 수 있게 하는 내결함성 메커니즘입니다.
- **PK sensorId로 파티셔닝**: Kafka Producer가 메시지를 보낼 때 이 값을 파티션 키로 사용하면, 같은 sensorId를 가진 메시지들은 항상 같은 파티션으로 가서, 그 센서 하나의 데이터 순서는 항상 보장됩니다(파티션 간 순서는 보장 안 됨).

## wsc2026-sensor-producer (EC2, Private)
- MSK 브로커에 메시지를 발행(Produce)하는 클라이언트 역할입니다. Private Subnet에 있으면서도 MSK와는 같은 VPC 내부 통신이므로 인터넷 경유 없이 도달 가능합니다.

## wsc2026-sensor-consumer / wsc2026-sensor-alert-consumer (Lambda, MSK Trigger)
- Lambda의 **이벤트 소스 매핑(Event Source Mapping)**이 MSK를 소스로 지정되면, Lambda 서비스가 내부적으로 지속적으로 해당 Topic을 폴링하며 새 메시지가 오면 자동으로 Lambda를 실행시킵니다. 이는 "Lambda가 스스로 Kafka Consumer 역할을 하는 상시 프로세스를 유지하지 않아도 되는" 서버리스 소비 패턴입니다 — 별도 EC2로 Kafka Consumer 앱을 24시간 띄워둘 필요가 없습니다.
- 각 Lambda는 서로 다른 Topic(`sensor-raw` vs `sensor-alert`)을 각자 트리거로 구독하므로, 원본 데이터 처리 로직과 알림 처리 로직이 완전히 독립된 함수로 분리됩니다.
- Lambda가 VPC 내부(Private Subnet)의 MSK에 접근하려면, Lambda 자체도 그 VPC에 연결(ENI를 통한 VPC 연결)되어야 합니다.

## wsc2026-sensor-data (DynamoDB 테이블)
- PK `sensorId` + SK `timestamp`: "이 센서의 시계열 데이터를 시간순으로" 조회하는 패턴에 최적화된 키 구조로, 지금까지 여러 번 반복된 "엔티티+시간" 복합키 패턴이 여기서도 재등장합니다.

## wsc2026-sensor-alert-bucket-<비번호> (S3 버킷)
- 오류 데이터 저장용으로, 정상 처리되지 못한 메시지나 알림 이력의 아카이브 역할을 합니다.

## wsc2026-msk-ec2-role / wsc2026-msk-lambda-role
- EC2 Role은 MSK에 메시지를 쓰는(Produce) 최소 권한, Lambda Role은 MSK에서 메시지를 읽는(Consume) 최소 권한 + DynamoDB 쓰기 권한만 가져야 합니다. IAM 인증 클러스터이므로 이 권한은 일반 EC2/DynamoDB IAM Action이 아니라 `kafka-cluster:*` 네임스페이스의 전용 액션으로 표현됩니다.

# 이 과제 전체를 관통하는 핵심 이론 요약

| 이론 개념 | 정의 | 적용 사례 |
|---|---|---|
| 워크플로우 오케스트레이션 | 여러 단계의 순서·재시도·분기를 선언적으로 관리 | Step Functions |
| 상태를 물리적 위치로 표현 | 별도 상태 DB 없이 파일 경로 자체로 처리 상태를 드러냄 | S3 input/processed/error |
| 발행-구독 스트림 | 여러 소비자가 동일 데이터를 독립적으로, 반복해서 읽을 수 있음 | Kinesis |
| 지속 쿼리 (Continuous Query) | 결과가 한 번에 끝나지 않고 계속 갱신되는 스트리밍 SQL | Flink |
| 감사 로그 기반 이벤트 탐지 | 모든 API 호출을 기록하고 위험 패턴만 필터링 | CloudTrail + EventBridge |
| 탐지-대응 분리 | 감지(Rule)와 실제 조치(Lambda)를 서로 다른 컴포넌트로 분리 | Event Handling |
| IAM 통합 인증 (Kafka) | 별도 ACL 체계 없이 IAM Policy로 스트리밍 접근 통제 | MSK |
| 파티션·복제 | 병렬성(Partition)과 내결함성(Replication)을 동시에 확보 | Kafka Topic |
| 서버리스 스트림 소비 | 상시 Consumer 프로세스 없이 이벤트가 올 때만 함수 실행 | Lambda MSK Trigger |
